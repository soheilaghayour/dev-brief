# Decisions

Judgment calls in force. Requirements live in [`docs/prd.md`](docs/prd.md); this file
links to them instead of restating them.

## Decisions

- **When two tools fit, pick the one German product-startup job ads ask for.** DevBrief is a portfolio piece; every extra piece of complexity needs a stated reason, here or in the PRD.
- **GitHub Issues are the backlog.** One home for planned work; a `backlog.md` would copy it and drift.
- **`CLAUDE.md` is the one home for agent rules; `AGENTS.md` only points to it.** PRD §4.2 asks for both files; two copies of the same rules drift apart.
- **`@/*` maps to `src/*` inside each app, and `packages/shared` is imported as `@devbrief/shared`.** The PRD names neither; one import style in both apps keeps moves cheap.
- **RSS items with a missing or unparseable date are skipped.** F1.2 doesn't cover the case, and substituting the fetch time would rank old posts as fresh.
- **Node 26 (the current Active LTS) and pnpm 12, pinned in `.nvmrc` and `packageManager`.** Tooling versions come from one place each; CI reads both.
- **Nest 12 is ESM-only, so the API and `packages/shared` are ES modules with `.js` import specifiers.** One module system across the repo; the web app is bundled by Next.
- **TypeScript stays on 6.0.x.** `typescript-eslint` doesn't support 7 yet; raise it when it does.
- **The `zod` advisory GHSA-mrhx-c7xc-m3w5 is ignored in `pnpm audit`; every request-input `z.array()` gets `.max()`.** Only 4.6.6 fixes it, and the PRD pins Zod 3.25 for `@a2ui/react` ([§4.1](docs/prd.md#41-system-diagram)); request bodies are capped at 100 KB ([§8.6](docs/prd.md#86-security-basics)). Remove the ignore when the pin lifts.
- **Prisma stays on 7.10.x.** The npm `latest` tag already points at an 8.0 release candidate; the PRD specifies Prisma 7 ([§4.2](docs/prd.md#42-monorepo-layout)).
- **`Verification` keeps the `identifier` index the Better Auth CLI generates, though PRD §5.2 omits it.** The CLI output is the authority for its models ([§5.1](docs/prd.md#51-phase-map)); the index serves its lookups by identifier.
- **`Story.searchVector` declares its generation expression as `@default(dbgenerated(...))` and its GIN index as `@@index`, though PRD [§5.2](docs/prd.md#52-prisma-schema) shows neither.** Without them Prisma sees drift against the hand-edited migration and would drop the index; CI runs `prisma migrate diff --exit-code` to keep it so.
- **`SourceItem.canonicalUrl` (indexed) stores each item's own canonical URL, though PRD [§5.2](docs/prd.md#52-prisma-schema) omits it; URL dedup matches it as well as `Story.canonicalUrl`.** A Story joined by title ([AC-1.2.5](docs/prd.md#f12-scheduled-ingestion)) keeps only its first item's URL, so a later item with a joined item's URL and a different title would otherwise create a duplicate Story.
- **Integration tests use their own database, `DATABASE_URL_TEST`.** They truncate every table, which must not wipe the dev data; migrations and tests read the same variable.
- **Uber Engineering is replaced by Shopify Engineering in the seeded RSS list.** Uber's feed URLs return 404 or 406; Shopify's `blog.atom` works and is a comparable engineering blog ([F1.2](docs/prd.md#f12-scheduled-ingestion)).
- **Local env lives in one root `.env`, loaded by `dotenv-cli` in each app's `dev` and `build` scripts; `dev` falls back to `.env.example`, so a fresh clone runs without a `.env`.** Next only reads its own folder's `.env`, and Node refuses `--env-file` in `NODE_OPTIONS`; a missing variable still fails fast at boot.
- **An `exclude` phrase vetoes a tag even when a source tag names it.** [Appendix A](docs/prd.md#appendix-a--tag-taxonomy-v1) runs excludes after source tags; a "Rust Belt" post tagged `rust` by Dev.to is still not about Rust.
- **`canonicalizeUrl` throws on a string that is not an http(s) URL.** Adapters parse upstream items with Zod and drop invalid ones ([CLAUDE.md](CLAUDE.md)); a silent fallback would let a broken URL become a dedup key.
- **`percentile` counts the item itself in its window.** The mid-rank formula in [Appendix B](docs/prd.md#appendix-b--ranking-formula) needs the item in `n`, which keeps p in (0, 1).
- **The API hand-rolls a small Zod pipe and generates OpenAPI with `zod-to-json-schema` instead of using `nestjs-zod`.** `nestjs-zod` declares peers up to Nest 11 and the API runs Nest 12; the pipe is 15 lines and `@nestjs/swagger` still serves the document.
- **The throttler counts one bucket per client IP across all routes.** The library's default key includes the route, which would turn the 120 req/min global limit into a per-route limit.
- **The Origin guard exempts the safe methods GET, HEAD and OPTIONS.** Express answers HEAD with the GET handler, and [§6.1](docs/prd.md#61-conventions)'s CSRF rule targets state-changing requests.
- **An oversized body answers 400 `VALIDATION_FAILED`.** [§6.1](docs/prd.md#61-conventions) has no 413 code and requires the status to match the code.
- **The web server's API calls carry `x-internal-token` (env `INTERNAL_API_TOKEN`) and skip the rate limit.** Server-side calls reach the API without Traefik and without `X-Forwarded-For`, so all visitors would share one 120 req/min bucket; the token is compared in constant time and the API port is not published.
- **The auth rate limit (10 requests a minute per IP) is skipped only when `AUTH_TEST_MODE` is on and the request carries the internal token.** The e2e suite signs in many times from one IP; §8.6 forbids `AUTH_TEST_MODE` in production, so production behaviour is the same, and a test-mode API still limits a request without the token or with a wrong one.
- **Health is `ok` or `degraded` (a source is stale or open); a down database answers 503 `UPSTREAM_UNAVAILABLE`, so `db` is always `ok` in a 200.** [§6.2](docs/prd.md#62-rest-endpoints--phase-1) names the fields but not their values.
- **A source whose kind has no registered adapter is recorded as `skipped`, not `failed`.** The seed lists Dev.to and RSS before their adapters exist; counting them as failures would open their circuits and mark every run `partial` ([F1.2](docs/prd.md#f12-scheduled-ingestion)).
- **The overall run is `failed` only when every source that ran failed, and `skipped` when none ran; skipped sources do not count.** [§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking) defines `partial` for "one source failed"; with no source left to succeed, `partial` would hide a total outage, and an all-skipped run recorded as `success` would show green during one.
- **An adapter reports `partial` through `FetchContext.reportPartial()`, and a partial source counts as a success for its circuit and health.** It returned usable items; `partial` stays visible in its run row (the reason in `error`) and makes the overall run `partial`.
- **Any GitHub response with `x-ratelimit-remaining` below 5 marks the source run `partial`, even on the last planned page; a response without the header does not.** This is the literal reading of [AC-2.4.2](docs/prd.md#f24-github-source), and it is testable; a missing header says nothing about the limit.
- **A missing `GITHUB_TOKEN` skips the GitHub source (`skipped`, "GITHUB_TOKEN not set") instead of failing env validation.** A fresh clone runs without secrets, unauthenticated search (10 req/min) is not worth supporting, and like a kind without an adapter it must not open the circuit.
- **A GitHub repo's title is `{full_name}: {description}` cut to 140 characters with a trailing `…`; its `excerpt` stays `null`.** [F2.4](docs/prd.md#f24-github-source) sets the title; repeating the description under it on the story page would only add noise.
- **"Last successful run" for `INGEST_ON_BOOT` means an overall run with status `success` or `partial`.** A partial run still refreshed the feed, so re-running at once on every restart would only hammer the sources ([AC-1.2.1](docs/prd.md#f12-scheduled-ingestion)).
- **Sources fetch in parallel but write to the database one source at a time.** Two sources inserting the same canonical URL or title at once would hit the unique constraint or split a Story; writes are cheap next to the network calls.
- **The ingestion lock is a Postgres advisory lock on its own `pg` connection, not the Prisma pool.** A session-level lock must be released on the connection that took it; it also frees itself if the process dies mid-run.
- **`pnpm --filter api ingest:once` builds the shared package and the API, then runs the compiled CLI.** tsx (esbuild) does not emit the decorator metadata Nest's injection reads, and the compiled API imports the shared package from its `dist`.
- **The HN fixtures in `apps/api/test/fixtures/hn/` are real Firebase payloads under a composed id list.** The issue's counts (100 ids, 3 jobs, 2 dead items) must be exact, so the list mixes ids recorded from `topstories`, `jobstories` and a scan of recent items.
- **A re-ingested HN item keeps the Story's first title.** Only the SourceItem title follows edits; re-tagging and title dedup stay stable for a Story.
- **The 4-min run budget covers the source fetches and the auto-summary step, not the database writes or the other post-run steps.** A hung write would hold the lock until restart; bounding it is left to the first issue that needs it. The auto-summary step fetches from three upstreams under the ingestion lock, so it checks the run's signal before each story and passes it to every fetch.
- **A source is `healthy` within 2 hours of its last success, `stale` after, and `circuit_open` while its circuit is open; `/health` and `/sources` share this one rule.** [AC-1.3.11](docs/prd.md#f13-feed-and-discovery) leaves 2-3 h undefined; one constant, `SOURCE_STALE_AFTER_HOURS`, is easy to change.
- **A source that has never finished a run (no `lastSuccessAt` and no `lastErrorAt`) is left out of `/health`, `GET /sources` and the `/stats` source count; its first failed run brings it in as `stale`.** A seeded source that can't run yet, like GitHub without `GITHUB_TOKEN`, would otherwise keep health `degraded` for good, show "1 of 13 sources behind" on every feed page, offer an always-empty sidebar filter and inflate the landing's source count. Skipped runs set neither field, while any real fetch does, so a broken source still shows. The rule is `hasCompletedRun()` in `sourceStatus.ts`.
- **The feed query selects only ids and sort keys in raw SQL; a Prisma read then loads the cards.** The keyset, tag, kind and full-text filters need `$queryRaw` ([§4.2](docs/prd.md#42-monorepo-layout)); loading sources and items through Prisma avoids hand-rolled JSON aggregation.
- **`POST /stories/lookup` drops repeated ids, keeping the first occurrence.** Order is the input order; a card twice in the result would only be noise.
- **Top keyset cursors are not snapshot-stable across a rank recompute.** A story whose score moves past the cursor may be skipped or repeated in an open scroll; the client dedups by id (AC-1.3.5) and a reload starts fresh.
- **A feed cursor is not bound to the personalisation params it was issued under; a client restarts paging when they change, keying its feed query by them.** The cursor holds only its last row's effective score and id, and other boosts give another order, so carrying it over would skip or repeat stories; checking the params would put them in every cursor for a case the client avoids.
- **Health is never cached and the API version comes from `APP_VERSION` (default `dev`).** A cached health answer would hide an outage.
- **An RSS adapter hands its etag and Last-Modified to the engine, which stores them on the Source after the run's items are saved.** Saving them at fetch time would let a failed write be hidden by a 304 on the next run, and the feed's items would never arrive.
- **An RSS item without a title or a usable link is dropped like one without a date; a relative link resolves against the feed URL.** F1.2 names neither case; a Story needs a title and an http(s) URL, and a feed's own address is the only base a relative link has.
- **An RSS item dated in the future is stored as published at fetch time.** Feed dates are author-written; a future date would otherwise keep the item at maximum freshness until that date.
- **An Atom entry's `<id>` is its guid, so `externalId = sha1(guid ?? id ?? link)`.** `<id>` is Atom's permanent identifier, unlike a link that can change scheme or path.
- **Markup-like text in a feed title or excerpt is stripped as HTML, while `a < b` stays.** §8.6 says all HTML is stripped, so an escaped `<Suspense>` goes too; only a `<` followed by a letter, `/` or `!` starts a tag.

- **Better Auth is pinned to 1.7.26 and gets Zod 4 through a scoped pnpm override.** Every maintained Better Auth line (1.3 and later) is written against the Zod 4 API and crashes on the workspace's Zod 3.25 pin ([CLAUDE.md](CLAUDE.md) item 21); the override covers only `better-auth`, `@better-auth/core` and `better-call`, so app code and the web bundle stay on Zod 3.
- **`effect` is overridden to ^3.22.1 under `@prisma/config`.** Better Auth's Prisma adapter brings the Prisma CLI into the production dependency graph, and the 3.20 it pins has the high advisory GHSA-7589-6fvf-x4pw; 3.22 is a compatible minor.
- **`/api/auth/*` is limited by a small Express middleware, not Better Auth's limiter, and has no internal-token bypass.** Better Auth either trusts a single-value `X-Forwarded-For` or needs the proxy's CIDR list; the middleware counts all auth paths together on Express's one-hop `req.ip` ([§8.6](docs/prd.md#86-security-basics)), and the web server never calls `/api/auth` server-side.
- **Better Auth's IP tracking is off.** It would store the raw client IP in every Session row, which [§8.6](docs/prd.md#86-security-basics) forbids; nothing reads the column.
- **A new user or a linked account needs an email the provider marks verified (GitHub: the verified primary email; Google: `email_verified`).** `trustedProviders` makes Better Auth skip that check when linking, so a `validateUserInfo` gate enforces [AC-1.5.3](docs/prd.md#f15-auth-account-saves-and-merge)'s "verified"; refusing unverified sign-ups too stops a stranger from squatting an email before its owner signs in.
- **GitHub requests only `user:email` (`disableDefaultScope`).** Better Auth adds `read:user` by default; `/user` returns the public profile without it ([§8.6](docs/prd.md#86-security-basics)).
- **Better Auth's origin and CSRF checks are switched on explicitly, and OAuth tokens are stored encrypted.** It turns both checks off whenever `NODE_ENV=test` or `TEST` is set; the app never uses provider tokens after sign-in, so a leaked row must not hold usable ones.
- **The test-mode sign-in route is a Better Auth plugin, registered only when `AUTH_TEST_MODE=true`, and that flag also needs a loopback `APP_URL`.** With the flag off the route does not exist (404); an unset `NODE_ENV` defaults to `development`, so the public origin is the check no environment mix-up can fake. The plugin creates the session through Better Auth's own cookie code, so tests exercise the real cookie settings.

- **Geist comes from `next/font/google`, not the `geist` package.** It self-hosts a Latin-only subset with `display: swap` as [§7.1](docs/prd.md#71-design-references-and-system) asks; the package ships every weight and subset unsplit. The build needs network access to fetch the font once. next/font's metric-matched fallback is `local(Arial)` only, which Linux and Android lack, so `globals.css` adds Liberation Sans/Arimo and Roboto fallback faces with the same overrides; without them the landing text reflows when Geist swaps in (CLS 0.23 on the CI runner, ≈0.08 on Android).
- **The shortcuts help dialog loads on first `?`.** The root layout wraps every page, and the landing budget ([§8.5](docs/prd.md#85-performance-budgets)) can't carry Radix Dialog for a dialog most visitors never open.
- **The landing page downloads Sonner only when a toast is pending.** Only someone who just deleted an account sees a toast there ([AC-1.6.2](docs/prd.md#f16-settings)), so every other visitor would download Sonner for nothing. The delete-account dialog queues its toast in `sessionStorage`, with a memory fallback, and the marketing layout's `PendingToast` loads the Toaster after the redirect. Memory alone would cover a client-side navigation, but storage also survives the full page load Next falls back to when a deploy lands mid-session.
- **The sidebar has Feed, Saved and Radar, and no Collections item; `g c` "Go to Collections" opens `/saved`, the collections overview.** Collections has no index route in [§7.2](docs/prd.md#72-routes-and-views), which makes `/saved` the overview, so an item would only repeat the Saved link.
- **E2E runs as the last steps of the `check` job, not as a second job.** One required check, and install, build and Postgres run once; the smoke tests need the built apps and a seeded database, which `check` already has.
- **The first-load JS budgets are measured from the build, not the original 90 KB.** Next 16 and React 19 alone weigh ≈135 KB gzip, so 90 KB can't be met by any code change. Each ceiling is the measured size plus 3 KB, rounded up to the next 5 KB (the 3 KB covers the structural growth below), kept in `apps/web/bundle-budgets.json` and listed in [§8.5](docs/prd.md#85-performance-budgets). What keeps the numbers there: Zod, Radix, Sonner, the account menu and the hotkey bindings load after first paint; TanStack Query lives in the `(app)` layout, so the landing page does not carry it; the error boundaries use a dependency-free `BareButton`. Sentry's build step adds a debug-ID snippet to every chunk (≈2.4 KB per route); turning off `sourcemaps` would remove it, but client stack traces would no longer be symbolicated, so it stays. tailwind-merge (≈8.5 KB) is the price of the design system: the header toggle and the reused `StoryCard` need `ui/Button`, and the marketing layout alone measures ≈152 KB. Lighthouse ≥ 95 on the landing page is the primary gate. The Phase 2 owner decision raises `/feed` to 200 KB and `/story/[id]` to 195 KB, later 200 KB under the plus-3 KB rule (`/` keeps 160; `/saved` is 200 KB, below), 10 KB of headroom for the features the PRD places on those pages: F2.5's follow/mute heart, F2.3's summary badge and `u` shortcut, and later F2.1's clustering. A feature PR must not raise a budget on its own.
- **The size gate is a script over the build output, not `size-limit`.** `size-limit` measures a bundle entry, not the scripts a route's HTML loads, which is what [§8.5](docs/prd.md#85-performance-budgets) defines. `apps/web/scripts/checkBundleBudgets.mjs` sums the gzip of the route's scripts (the HTML for prerendered routes; the build manifests, which list the same files, for server-rendered ones) against `apps/web/bundle-budgets.json`. Before measuring, the gate checks that the manifest rule reproduces the HTML of the prerendered `/saved` (same route group), so a Next upgrade or a new `(app)` boundary file cannot make it under-count silently.
- **Mobile navigation and mobile filters are two separate sheets, both loaded on first open.** The menu opens a left drawer with the navigation; filters open a bottom sheet (AC-1.3.12), so the filter UI is rendered once per breakpoint and never inside the drawer.
- **The shortcut registry treats a sequence's first key as pending for 1 s.** A plain single-key shortcut does not run in that window, so `g` then `s` (go to Saved) never also fires `s` (save).
- **The rank recompute loads the 7-day window into memory and writes it in transactions of 500 updates through Prisma.** About 3k stories plus their items fit comfortably; raw bulk SQL would break the principle that raw SQL appears only where the Prisma client can't say the query ([§4.2](docs/prd.md#42-monorepo-layout), and the `$queryRaw` decision below).
- **The daily `TagDailyStat` window is today plus the two UTC days before it, and a story counts once per tag on its UTC publish day.** [AC-1.7.3](docs/prd.md#f17-platform) says "last 3 UTC days" without saying whether today counts; including it lets the copilot's "Not enough coverage" briefing ([AC-3.1.7](docs/prd.md#f31-copilot)) rank its suggested tags by the 7 UTC days ending today, today's stories included. Today's row stays partial until the next ingestion run or the daily job recomputes it.
- **Radar "Top movers" sort by absolute change `|current − previous|`, then slug, and `deltaPct` is `null` ("new") when the previous window is 0.** This reproduces the [§7.3](docs/prd.md#73-wireframes) wireframe order, and sorting by percentage would put "1 → 3 = +200%" above real movement.
- **The radar's "engagement" is the raw sum of `TagDailyStat.engagementSum`, which mixes HN points, Dev.to reactions and GitHub stars on their own scales.** [AC-1.7.3](docs/prd.md#f17-platform) stores no normalised figure per tag; a percentile-weighted count (`storyCount × avgPercentile`) is the alternative if the mix proves misleading.
- **Both radar windows end on yesterday (UTC), the last complete day, and an ingestion post-run step recomputes `TagDailyStat` for yesterday and today.** Comparing a partial today against full days made every steady tag look like it was falling (about −13% all day, −27% before 03:15 UTC), because the daily job is the only other writer. The post-run step keeps yesterday's row complete soon after midnight; the 03:15 job still rolls up three days. Today's row is never read by the radar.
- **The radar chart is Recharts, fetched with a plain `import()` after mount behind a fixed-height skeleton, and drawn without animation.** The PRD names Recharts. `next/dynamic` would not do: a server-rendered dynamic import is preloaded into the HTML and counts as first-load JS, and the lazy `import()` keeps the chunk out of every route's first load, `/radar` included. With animation off the chart is identical under `prefers-reduced-motion`; dash patterns next to the `--chart-1`…`--chart-5` colours keep the lines apart without colour.
- **The `/saved` first-load budget is 200 KB, `/story/[id]` is 200 KB (192.2 + 3 rounds up to 200), `/radar` is 195 KB, and app-route ceilings are the measured size plus 3 KB, rounded up to the next 5 KB.** Recharts widens Turbopack module ids from 5 to 6 digits (≈1.3 KB on every `(app)` route), and Turbopack's chunk splitting adds about 1 KB of structural growth per app route. `/saved` measured 194.8 KB against 195, so it had 0.2 KB of headroom. The #139 review found no cheap trim: the large parts are tailwind-merge, nuqs, TanStack Query and the Sentry snippet, which the owner keeps. Measured today: `/` 160.0, `/feed` 196.8, `/saved` 194.8, `/story/[id]` 192.2, `/radar` 189.0, `/collections/[slug]` 185.8 ([§8.5](docs/prd.md#85-performance-budgets)).
- **The size gate also fails when a first-load script of `/`, `/feed`, `/saved`, `/story/[id]` or `/radar` contains a forbidden module (Recharts, `@a2ui/react`, `@a2ui/web_core` and `lit`).** Minified code keeps string literals, so Recharts is recognised by its `recharts-` class names (`recharts-wrapper`, `recharts-surface`, …), the A2UI packages by `a2ui-react-` and `ValidationConfig.allowedMessages` (an internal error message), and lit by `litHtmlVersions`; the budget alone would not catch a static import on `/radar`.
- **Radar chart tags are picked with a checkbox per movers row; without `tags` in the URL the top 5 movers are ticked, and the last ticked tag cannot be unticked.** Unticking the only tag would write an empty `tags`, which the API reads as "top 5 again", so the table would tick five boxes right after the user cleared one.
- **`NuqsAdapter` lives in the `(app)` layout, not the root layout.** The landing page must not ship nuqs; the feed and story pages are dynamic on their own (`searchParams`, a dynamic segment), and Saved stays static.
- **Next's `/api/*` rewrite exists only when the build-time env `API_PROXY_URL` is set.** `next dev` and the e2e build set it; production builds leave it unset because the real proxy routes `/api/*`, and `typecheck` and `build` need no env.
- **Web code loads `lib/api/endpoints` on first use (`import()` inside the query functions) and `@devbrief/shared` is `sideEffects: false`.** Together they keep Zod and every contract out of first-load JS. The limits the web needs from the feed contract live in `contracts/feedLimits.ts`, apart from the schemas, because importing a constant from a module that builds Zod schemas pulls Zod in.
- **The search, sort and filter slots render on `/feed` only, and the mobile "Filters (n)" bar is a slot of the shell.** On Saved and Story they would edit URL params that page does not read.
- **The e2e seed replaces all stories and saves, resets every source to healthy with its circuit closed, and uses fixed story ids.** Health dots and `focus` deep links are then deterministic. It refuses to run unless the database name ends in `_test` or `e2e`, or `ALLOW_DESTRUCTIVE_SEED=1` (CI sets it); it lives in `apps/api/prisma/seedE2e.ts`.
- **Filter changes use nuqs' shallow `history.replaceState`, not `router.replace`.** A non-shallow replace would re-run the dynamic feed page on the server and prefetch twice; the URL stays the single source of truth.
- **The server prefetch for `/feed` never retries, and the search input stops at 100 characters.** A failing API must not delay the HTML by the retry back-off (the browser retries), and the contract's `q` maximum is 100, so the UI can't produce a 400.
- **Playwright sends `x-internal-token` on every browser request.** One test run is one visitor, so the per-IP limiter is not exercised by e2e.
- **A guest can keep 500 saves, and a full list refuses new ones with a toast instead of dropping old ones.** 500 is what one `POST /me/merge` accepts ([§6.2](docs/prd.md#62-rest-endpoints--phase-1)), so every local save can reach the account; silently evicting a save would lose data the guest chose to keep.
- **The "Saved on this device" toast and the storage-unavailable warning each show once per tab session, tracked in `sessionStorage` with a memory fallback.** [AC-1.4.1](docs/prd.md#f14-guest-saves) and [AC-1.4.4](docs/prd.md#f14-guest-saves) say "once" without defining the scope; when storage is unavailable, the warning replaces the first save toast.
- **`/saved` fixes its list of ids when it first shows; saves made there change what is shown but trigger no new lookup.** Unsaving a card removes it at once and moves the active card to its neighbour; a re-save happens in the feed.
- **The guest hint is a fixed banner at the bottom of the screen, shown to guests only.** It appears after hydration, so in the page flow it would push the feed down ([AC-1.3.9](docs/prd.md#f13-feed-and-story-page) holds CLS under 0.05); a signed-in user never sees guest copy.
- **Open tabs follow each other through the `storage` event, and every save re-reads storage before changing it.** Each tab would otherwise write its whole list over the other's.
- **Guest data written by a newer app version is left untouched: the store runs in memory instead.** After a rollback, overwriting it with the older shape would erase saves.
- **`merged.saves` counts the distinct existing stories in a merge request, whether or not they changed a row; `skipped.saves` is the number of unknown story ids.** [§6.2](docs/prd.md#62-rest-endpoints) doesn't define the two counts; this keeps a repeated merge answering the same and makes the "N saved stories synced" toast ([AC-1.5.5](docs/prd.md#f15-auth-account-saves-and-merge)) count what the user now has in the account.
- **The synced toast reads "1 saved story synced" for one save, and nothing shows when no story was merged.** [AC-1.5.5](docs/prd.md#f15-auth-account-saves-and-merge) words only the plural; "1 saved stories" reads as an error.
- **The device releases every save it sent once the server confirms, unknown stories included.** A story the server doesn't know is gone for good; keeping it would resend it on every load.
- **A signed-in load merges whenever the device holds saves or preferences; `pendingMerge` only records an attempt the server hasn't confirmed, and it joins the v1 guest store without a version bump.** It is set before the request and cleared on the server's answer, so a tab that dies mid-request still counts as a failed attempt; stored v1 data without the field reads as `false`, so the `devbrief:guest:v1` key and the `version: 1` shape of [AC-1.4.2](docs/prd.md#f14-guest-saves) stay.
- **Per-user limits (merge 10/min, mutations 60/min) use a small guard after `AuthGuard` instead of `@nestjs/throttler`.** The global throttler runs before `AuthGuard`, so it can't key on the user; a second `ThrottlerGuard` would still need its own tracker and storage for two buckets ([§8.6](docs/prd.md#86-security-basics)).
- **While `GET /me` is pending, `useSaves()` and `usePreferences()` are not ready and changes go to the device store.** A guest's first save or mute never waits on the network, and a change made before sign-in is recognised is picked up by the merge.

When fewer than a page-plus-one stories match at all, those first stories are the whole answer and the streams are not read: they would scan the whole index for a floor of -infinity (about 500 ms for a source with five stories). A `sources` filter on a boosted Top page is resolved to a list of story ids when the sources hold at most 500 items (one capped probe of `SourceItem`), because the planner assumes any source matches a large share of stories and walks the index with a per-story lookup (about 250 ms per scan), while a list of ids is looked up by primary key. A larger source stays an `EXISTS`, which walks the rankScore index and stops after a page; resolving it to ids instead made a source holding every story about 100 times slower, as the planner cannot size a subquery and drives all three reads from it. Pages are re-sorted by the true key, so the streams never repeat a story, but one case can skip a story while paging: two followed stories with exactly equal rankScore at the page cut, plus a third whose rankScore is one ulp away and collides with theirs under ×1.5 (3.5411337216615677 and 3.5411337216615673 both boost to 5.311700582492351). It is accepted because [Appendix B](docs/prd.md#appendix-b--ranking-formula) scores essentially never collide like this.
- **The small-source id list applies to every feed page with a `sources` filter: unboosted Top and Latest too.** Measured at 40k stories, an unboosted Top page on a 5-story source took about 330 ms p95 and Latest about 560 ms, as the planner walked the whole `(rankScore, id)` or `(publishedAt, id)` index; with the id list they take about 30 ms. A source above 500 items pays the capped probe (about 20 ms) and keeps its `EXISTS`.
- **A guest's `prefs` join the v1 guest store without a version bump, and a stored set that fails `PreferencesSchema` reads as empty.** Stored v1 data without the field reads as empty preferences, the `pendingMerge` rule, so the `devbrief:guest:v1` key of [AC-1.4.2](docs/prd.md#f14-guest-saves) stays; a set that breaks one rule (a cap, a value both followed and muted) can't be trusted in part, and sending it would fail the whole merge.
- **A follow or mute that would take a list past `FEED_LIST_MAX` is refused with a toast.** A longer list would make every feed request and the merge fail validation; dropping an older entry would undo a choice the user made, as the 500-saves rule avoids.
- **An account change sends the full preference set with `PUT`, built from the stored set, which is fetched first when it hasn't loaded.** `PUT` replaces the set, so a change built on an empty placeholder would erase the account's other preferences.
- **The landing preview ignores preferences.** It is static and shows the same stories to everyone.
- **A signed-in visitor's first page is rendered with their preferences; a guest's muted cards leave at hydration.** The server forwards the session cookie, reads the account's preferences and asks the feed for the page they give, so a muted story is never in the HTML. It can't read a guest's `localStorage`, so a guest's server-rendered page can show a muted card until the page hydrates; then the stored mutes are read synchronously and the card is gone before the next paint, and the page stays filtered while the personalised one loads. A skeleton in place of the rendered page would cost more than that one flash ([AC-2.5.2](docs/prd.md#f25-followmute)).

- **Auto candidates come from the 7-day Top window.** Older stories keep a frozen `rankScore` ([Appendix B](docs/prd.md#appendix-b--ranking-formula)) and never appear in Top.

- **Clustering needs `AUTO_CLUSTERING=true` as well as `FEATURE_CLUSTERS=true`; it defaults to `false`.** Same reason as `AUTO_SUMMARIES`: a key and the feature flag alone must not start spending on every ingestion run, so the live calls have a switch of their own that defaults to off and that production sets with the flag.

- **A new story is matched only against stories that were decided before it.** The pool leaves out the run's not-yet-decided new stories, so no story is paired by an earlier story's decision and then decided again (F2.1: S is single when decided).
- **A run makes at most 100 clustering calls, and the step ends after 3 unexpected errors in a row; one unexpected error on its own leaves that story single and the step goes on.** The cap keeps the run's 4-minute budget shared with the auto summaries; the rest of a first run's backlog stays single, like any capped decision. At about 17 new stories per hourly run the maximum binds only after downtime or a backfill, and a test pins the constant. Three database errors in a row mean the database is down, which a fourth story would not fix.
- **`sameLink` is true for the same GitHub repo (any path inside it), or for the same host without `www.` where one path is a segment-wise prefix of the other and the shorter path isn't `/`; equal paths need equal queries.** On hosts that carry many projects (github.com, dev.to, medium.com, youtube.com and their subdomains such as `m.youtube.com`) only the repo rule applies, since a shared host there says nothing, and `watch?v=a` is not `watch?v=b`. Entity tokens take no host at all: two posts of one blog are not duplicates.

- **Candidate scoring computes the trigram similarity of `pg_trgm` in TypeScript, over a pool loaded once per run, instead of calling `similarity()` per new story.** At the production-sized window (1,200 stories, 400 new) the per-story `similarity()` query ran ≈560k comparisons as a sequential scan and, with the entity tokens recomputed per row, took ≈19.6 s against the 5 s of [AC-2.1.2](docs/prd.md#f21-clustering-ai-assisted); scoring in memory takes ≈1.2 s. The score is the same number (Jaccard over padded trigrams), and a test compares it with `similarity()` for every pair of fixture titles. The trigram index from the migration is then unused by the step; it stays because the migration is applied.
- **The pre-filter scores `0.45·trgm + 0.45·ent + 0.10·link` against a floor of 0.16, with "AI" on the entity stoplist and a shared CVE or GHSA id counting as `link = 1` ([F2.1](docs/prd.md#f21-clustering-ai-assisted) rule 1).** Real reports of one event are worded far apart and often share only one name, such as "nginx" or "CrowdStrike". At the old 0.55/0.35 weights and 0.20 floor, the held-out pairs pass 13 of 23 positives. The held-out pairs are real stories, labelled before any constant changed. Together the four changes pass 18 of 23 held-out positives (78%) and 24 of 25 on the main fixture (96%); `cluster-pairs.confirm.json` holds 11 more positives and as many negatives, labelled by the rule below before they were scored and never used to tune: its positives gate the pre-filter at 75%, and a failure there goes to the owner, not to the constants. Tuning on the held-out set makes it a gate for the pre-filter, not a blind set; it stays blind for the prompt and `CLUSTER_MIN_CONFIDENCE`. A patch version still counts as its release line: "26.5.0" and "26.5" share a token, and "SQLite 4" is read as 4.0 only against the same name. The floor only decides whether a call is worth making. The options were measured in cost order:
  - Floor and weights alone reach 18 of 23 only at a floor of 0.14, which sends 132 of 400 snapshot stories a day to the model.
  - "AI" is in 72 of the 281 recorded snapshot stories and names nothing, so dropping it frees calls.
  - A shared advisory id is the one cheap identifier that found a pair without adding calls.
  - Sending top-K candidates whenever an entity is shared would call for 58% of stories.

  - `clusterCallRate.test.ts` measures the call rate and the estimated input on the recorded snapshots and on `test/fixtures/hn-window`, four real HN days with a production-sized window; the snapshots' windows are much smaller than production's, so they understate the rate, and both are tested.
  - The per-call cost is unverified until [#82](https://github.com/soheilaghayour/dev-brief/issues/82) records real usage; a test then checks it.

The TLD list keeps names like "Node.js/Deno" valid text.

- **Prompts live in `apps/api/src/modules/llm/prompts/` as §8.2 says, although only the summaries module uses this one.** Phase 3 adds the copilot prompt beside it.

The auto step stops waiting when the run's signal aborts. Across instances (only a rolling deploy runs two) the unique `Summary.storyId` is the backstop: both write on the representative, the loser's insert hits P2002 and it returns the stored summary as `raced`, keeping its quota slot because its call was paid. Single stories, and every story with the flag off, skip the map.

- **A user has at most 50 collections and a collection at most 500 items; a manual add over a limit answers 400 `VALIDATION_FAILED`, and the merge keeps to the same limits, reporting the overflow as `skipped.collections` and `skipped.items`.** Merged collections beyond the 50th (in request order) are not created and items beyond a collection's 500th are not added, because a merge that ended over a limit would leave an account no manual action could bring back under it; the counts let the client say so instead of dropping data silently. A merge request may not repeat a slug (400).
- **`PUT /me/collections/:id/items/:storyId` answers the updated `Collection`, and a collection item takes its `userId` from the collection's owner, never from the request.** The schema would allow an item whose `userId` differs from its collection's owner (PRD §5.2); this way an item can only point at its owner's own save, and the body carries no user.
- **Positions of collections and of a collection's items are dense, 0-based, and kept dense by bulk statements whenever one moves, is deleted or is unsaved.** A client can send "move to index n" without knowing the gaps; one range shift instead of a row-by-row rewrite keeps unsaving a story that sits on many large boards inside the transaction timeout.
- **Collection writes take a per-user advisory lock with `pg_try_advisory_xact_lock`, retry 3 times 50 ms apart, then answer 409 `CONFLICT`, which the client may retry.** Waiting on the lock would hold a database connection per waiting request and starve everyone else's reads; `CONFLICT` is a new error code because no existing one means "busy, try again".
- **An empty note (`""`) counts as no note: `PATCH` stores `null` and the merge ignores it.** One way to say "no note" keeps the editor's cleared text and a never-written note the same thing.
- **A note merge that conflicts appends the guest note after `\n\n---\n\n` unless the server note equals it or holds it as one whole `---`-separated segment; a combined note over 20,000 characters keeps the server note and counts the story in `skipped.notes`.** A repeated merge appends nothing, so the merge stays idempotent (bite 18), and whole-segment matching, unlike a substring check, does not drop a short note like "TODO" that the account note merely contains. A skipped note is lost on the device once the client confirms the merge; the alternative, keeping it on the device, needs a way to stop it being resent.
- **The merged note takes the guest note's `updatedAt` as its `noteUpdatedAt`; a note for a story the account has not saved saves the story.** The date is then a function of the request, so a repeat changes no row, and a guest note always belongs to a saved story.
- **`merged.collections` counts distinct guest slugs, `merged.notes` counts stories whose note was set or already present, and `skipped.saves` counts every unknown story id of saves, collection items and notes together (so a toast must not word it as "N saves skipped").** Each counts what was processed, whether or not it changed anything, like `merged.saves`.
- **The merge's `collections` and `notes` work with `FEATURE_COLLECTIONS` off; the note fields of `Save` and the saves list are omitted while it is off.** The merge route is unflagged and the inputs are additive; omitting the fields keeps flag-off responses identical to Phase 2.
- **The copilot prompt cuts each story to 300 tokens but shrinks that cap when the whole input would pass 6,000 estimated tokens.** [§8.1](docs/prd.md#81-llm-cost-model-claude-haiku-55-010--1m-input-050--1m-output-for-prompts--100k-tokens) sizes the input at a fixed 1,728 tokens (system and plan schema) plus 15 stories, so 15 full stories would reserve more than the $0.00135 the copilot cap is sized for. With 15 stories each gets about 277; with fewer, 300. The question is cut at 200 characters in the prompt only: retrieval searches the whole question.
- **A streamed plan gets no schema retry, and a provider retry only before its first token.** The ledger rules of `generateStructured` apply per attempt (reserve the worst case, settle at actual usage; an error status settles at zero, a timeout, abort or lost connection at the worst case; a refusal or invalid plan at its reported usage). But a retry after sections reached the client would show them twice, and a plan that fails its schema after streaming has already cost one attempt's tokens; the endpoint reports the failure ([AC-3.1.8](docs/prd.md#f31-copilot)) instead. A consumer that stops reading settles the open reservation at its worst case and aborts the provider call.
- **A stream's 30 s total and 10 s first-token deadlines are `LlmService`'s own timers, started once per call, so a retry gets only the time left ([AC-3.1.9](docs/prd.md#f31-copilot)).** The SDK's `totalMs` is an `AbortSignal.timeout`, which Vitest's fake timers can't advance, and its `firstChunkMs` restarts with every attempt. The pause before a retry ends early when a deadline passes or the caller aborts.
- **Copilot retrieval reads the feed query twice (the question's tags, then its keywords), unions the cards and keeps the best 15; the keyword read is the feed query's internal `ftsMode: 'any'`, and retrieval adds no `$queryRaw`.** `FeedService.readFirstPage` skips the response cache, so a retrieval never sees a page up to a minute old, and takes the whole question: the 100-character cap is the HTTP contract's. The public `q` needs every piece of its input ([AC-1.3.4](docs/prd.md#f13-feed-and-story-page)), so a natural-language question would match nothing. `ftsMode: 'any'` builds `to_tsquery('english', 'kw1 | kw2 …')` from the question's words minus the named filler list (`QUESTION_FILLER`: `week`, `team`, `what`, and the words the English text search ignores), requires 2 matched keywords when the question has 2 or more, takes the best 15 by `ts_rank_cd`, and the union is ordered by `rankScore`. Retrieval does not go through the public `q`. A question whose keywords are all filler matches nothing. A subject outside the taxonomy with a single keyword ("Rust vs Go" gives only `rust` and `go`) can still end in `no_coverage`.
- **A plan title that holds a URL or markup, or passes 80 characters, ends the call with `invalid_output` before any message is sent; a section that fails its schema is skipped and logged, and the briefing fails only when no section is left.** The title becomes the `root` component's literal title and reaches the client unchecked otherwise, so it gets the same plain-text gate as a section. Skipping follows [§6.4.4](docs/prd.md#644-llm-output-contract-briefingplan-compiled-to-a2ui) rule 6: one bad note shouldn't discard the other sections already paid for. The SDK validates the plan's structure only, with a malformed section parsed to `null`, so a skipped section can't fail the final output. The title is released only once a later key exists, so it is whole, and no section before it, whatever order the model writes the keys in.
- **The pipeline sends nothing before the plan's title, so `createSurface`, the empty `root` and the subtitle arrive together.** A spent cap or a failure before the first token therefore leaves the client with no message at all, which is what lets the endpoint answer with the fallback or refund the quota ([AC-3.1.8](docs/prd.md#f31-copilot)). The renderer shows its skeleton until `root` arrives either way ([AC-3.1.2](docs/prd.md#f31-copilot)).
- **The compiler drops a takeaway or consensus point that cites only unretrieved stories, keeps the valid ids of one that cites some, and keeps a point that cites none; a plan with no section left fails with `invalid_output`.** An uncited claim is the model's summary, but a claim whose every source is invented is unsupported. A briefing of only `root` would be an empty answer that still costs a quota.
- **While the copilot recordings hold `"placeholder": true`, their recorded-reply tests skip with a warning, and the placeholders break those checks on purpose.** Same rule as the summary and clustering recordings: a hand-written reply proves nothing about the model. Deleting the flag without recording then fails the test instead of passing, and a test that runs only while the flag is set asserts that the placeholder does break them. The owner records the real streams in [#97](https://github.com/soheilaghayour/dev-brief/issues/97) before `FEATURE_COPILOT` goes on in production.
- **The copilot checks in this order: feature flag, Origin, IP window, body, 24 h cache, quota slot, then retrieval and the model.** A cached answer costs no quota, and a full quota is still a JSON 429 only if it is answered before the stream's headers go out. The slot is therefore taken before retrieval, and a thin-coverage answer ([AC-3.1.7](docs/prd.md#f31-copilot)) gives it back, so its net quota use is zero; the cost is that a requester already at the limit gets 429 even for a question that would have had no coverage.
- **A question is normalised by Unicode NFKC, lowercase, trimmed, whitespace collapsed and trailing sentence-ending marks (`? ! . … , ; :`) dropped, then hashed with sha256.** That is what makes `"  What were THIS week's TypeScript tooling debates?? "` and its plain form one cache key without merging questions that differ inside (`Rust vs. Go`) or by a character that ends a name (`C#` and `C`, `Rust (2024)`). A question that normalises to nothing (`???`) is a 400.
- **A cached replay writes no `CopilotQuery` row and sends the cached row's id as `queryId`.** A row per replay would make the 30-day history list one answer many times and would extend the cached answer's life through its copies; the reader sees the same id for the same briefing.
- **"Closest example" is the `ExampleBriefing` whose question shares the most `tagStory` tags with the asked question, ties and zero overlap going to the lowest `position`.** The examples are three fixed questions, so tag overlap is enough to pick the nearest topic without embeddings.
- **The copilot slot is given back when a spend cap sends the example, when coverage is thin, and when a failure comes before any section component; it stays used when a section went out.** A reader who got a fallback or nothing was not served by the model; a reader who saw part of an answer was. The opening `root` carries no answer, so it doesn't count as a section. A client hang-up follows the same rule.
- **A guest's quota is the device counter (3) plus an IP backstop counter (10), and a question takes a slot in both or neither.** The backstop stops rotating device ids ([AC-3.1.4](docs/prd.md#f31-copilot)); a guest whose backstop is lower than the device quota is told that lower remaining count.
- **`meta` is written together with the pipeline's first event, not before the model is called.** The spend reservation is inside the model call and its refusal is the only way to know the answer is a fallback; the headers and a `: ping` are flushed at once, so the first byte still leaves within 100 ms.
- **A guest's collections join the v1 guest store without a version bump, and a stored set is salvaged entry by entry, like saves.** Stored v1 data without the field reads as `[]`, the `prefs` rule, so the `devbrief:guest:v1` key stays. An invalid collection or item is dropped, the first of a repeated slug, id or story is kept, and a set over 50 collections or 500 items keeps its first 50 or 500; one bad entry must not cost the user every board. A stored `collections` that is not a list at all can't be told apart entry by entry, so it reads as empty and the guest store stops writing to `localStorage` for that page, leaving what is stored untouched. Names, slugs (`collectionSlug`, kept on rename) and the 50 / 500 limits come from `packages/shared`, so a guest board and its account twin match by slug ([AC-3.4.5](docs/prd.md#f34-collections-notes-and-digest)).
- **Unsaving a story, and purging a save whose story no longer exists, remove it from every guest collection; the removal of saves a confirmed merge makes does not.** A story that is gone can't be shown on a board, so its items would only inflate the counts. Stripping boards with the saves a merge releases would delete boards that are still in the same request or a later one. A board also drops, from its own collection, the stories its lookup reports as gone.
- **A guest collection change over a limit is refused with a toast and nothing is dropped, and adding a story that is not saved saves it first.** The same rule as the 500-saves refusal; saving first matches `PUT /me/collections/:id/items/:storyId` (row 28). A save list already at 500 refuses the add, because one more save would exceed what a merge accepts.
- **Collections reorder with Move up / Move down menu items, not drag and drop.** [AC-3.4.1](docs/prd.md#f34-collections-notes-and-digest) asks for reordering without naming a gesture; menu items work by keyboard and touch and add no library to a budgeted route.
- **An account's collections come from `GET /me/collections`; the items of a board are fetched only for the boards a component asks for (`useCollectionItems`).** The list carries counts, so the sidebar needs one request, while the "Add to collection" ticks, a board and a digest scope need the items of each board they show. A change is optimistic ([§7.5](docs/prd.md#75-state-management-strategy)); changes are sent one after another so a rename and a move can't arrive reversed, and a rollback is skipped while a later change is in flight, since its snapshot would undo that change's patch. A change cancels and refetches only the entries it patches (the list and its own board), never the `['collections']` prefix, and a write that meets the account's busy lock (409 `CONFLICT`) is sent again after 250 ms and 500 ms before it rolls back with "busy syncing". The sidebar and the add button read a board's items from the query cache and re-render when it changes, instead of observing every board with `useQueries`, which costs about 2 KB in first-load JS that `/saved` can't spare under its budget in `apps/web/bundle-budgets.json`; only the lazy dialog, board and digest chunks use `useQueries`, through `useCollectionItems`. The board loads its cards with the story lookup like a guest board, one request more than `GET /me/collections/:id` alone, so the guest and account boards share their code.
- **The collections sidebar and the board are fetched after first load (`next/dynamic`, `ssr: false`), and the dialogs and menus on first open.** Both show only what the device stores, which the server can't render, and keeping them out of first-load JS holds `/saved` under its ceiling. `/collections/[slug]` has a budget of 190 KB, the [§8.5](docs/prd.md#85-performance-budgets) ceiling: the lazy command bar imports 49 modules the page's first load also uses, and Turbopack splits those shared modules into an extra chunk, costing about 1.0 KB gzip in the split against about 0.4 KB of real code, with no cheap way back.
- **The example briefings are billed to the `copilot` ledger feature, and `briefings:generate` replaces all rows or none.** [§5.2](docs/prd.md#52-prisma-schema)'s `LlmFeature` has no value for examples, and the run uses 3 of the day's 20 fresh-question slots under the copilot cap, and its cost is in [§8.1](docs/prd.md#81-llm-cost-model-claude-haiku-55-010--1m-input-050--1m-output-for-prompts--100k-tokens). A partial set would leave a landing tab missing, so every question's story count is checked before any model call, all results are held in memory, and one transaction swaps the rows at the end: a question with fewer than 3 stories or a failed generation changes nothing.
- **`briefings:generate` runs only with `--confirm-database <name>` matching the database in `DATABASE_URL`.** It spends money and replaces rows, and a developer shell often has a production URL in its environment: typing the name is the explicit pointing.
- **The header's Ask button ([AC-3.1.1](docs/prd.md#f31-copilot)) and the `⌘K` / `Ctrl+K` shortcut share one launcher, fetched right after hydration like the hotkey bindings (`next/dynamic`, `ssr: false`); the launcher loads the bar on first open.** The button appears with its chunk, in a placeholder of the button's width (the button has a fixed width, so the key cap's text, `⌘K` or `Ctrl K` by platform, never moves its neighbours).
- **`⌘K` / `Ctrl+K` works while focus is in an input.** It is a modifier chord, so it cannot collide with typing; the editable-element rule covers single keys only (CLAUDE.md bite 25). The shortcut also stops the browser's own `Ctrl+K`.
- **Following a link inside the briefing (a story, a footnote to a story, a tag) closes the bar, and a new open starts empty.** The bar is a modal: left open over the story page it would hide what the reader came for, and keeping its briefing alive across closes would need a store for little gain. A ctrl-click or a footnote that only scrolls to its card leaves the bar open. Focus goes back to what had it when the bar opened, or to the Ask button when that element has left the page.
- **Closing the bar or asking a new question aborts the running stream, and the server settles it by its own refund rules.** The client never decides a refund: a reader that leaves after a section keeps the slot used, as [AC-3.1.8](docs/prd.md#f31-copilot) says.
- **Single-key shortcuts and `g` sequences stay quiet while any dialog or sheet is open.** The page behind a modal is inert, so `s` or `j` there would save a story the reader cannot see; `⌘K` and `Esc` still run.
- **The quota badge is read again from the server when an answer ends or fails.** The server refunds some failures (AC-3.1.8), and the client never decides a refund, so the badge shows what the server says.
- **The per-IP limit on `/copilot/ask` and the summary route skips a request carrying the internal token,** like the global limit: one e2e run is one visitor. A cached replay still counts for a real visitor ([§8.6](docs/prd.md#86-security-basics)).
- **A stream event this client does not know, data that is not JSON, and a single invalid `a2ui` message are skipped, not failures.** The server can add an event without breaking old clients, and the renderer drops one bad message the same way; a `meta`, `error` or `done` that breaks its schema is still a failed answer.
- **`eventsource-parser` stays on 3.1.1, the version the AI SDK already resolves.** It adds no package to the lockfile; 4.x brings nothing the stream parser needs.
- **The quota badge stays hidden until the quota is known, and a failed `GET /copilot/quota` is not an error.** Asking still works, and the first `meta` or the 429 supplies the count.
- **The e2e suite covers the cached and no-coverage paths; live generation is covered by API integration and component tests.** CI never calls the live LLM ([§8.7](docs/prd.md#87-testing-and-ci)), the same rule as for summaries.
- **A guest's notes join the v1 guest store as `notes: { [storyId]: { note, updatedAt } }`, parsed entry by entry, and `useSaves()` carries them (`note`, `setNote`, `savedAt`).** A note belongs to a save ([§5.2](docs/prd.md#52-prisma-schema)) and has no hook of its own in [§7.5](docs/prd.md#75-state-management-strategy). A stored note over 20,000 characters, empty, or with a bad id or date is dropped alone; writes go through `SaveNotePatchSchema`, so `""` is stored as no note. Unsaving or purging a story deletes its note; a confirmed merge keeps notes, like collections, until they have synced.
- **An account's note is read from whichever cache holds it (the story's own save, the saved list, a board) and is loaded with `GET /me/saves/:storyId` only when none does.** The story page is public and cached, so it knows nothing of the note; the editor does not open before the note is known, since typing over an empty text would overwrite it. A write cancels and patches only the entries that hold the story (its own save, the saved list, the boards with it), puts back only that story's note fields on failure, and refetches what it cancelled, so a list that was loading is never left stuck. The editor keeps the typed text, at module level per story, so a closed and reopened editor shows it again "retrying", and sends it on the next change or blur; "Saved" shows only when the newest write is confirmed. Notes of one story are sent in order. As the page closes the note goes out as a `keepalive` request, best effort (the browser caps such a body at 64 KB); if an older write is still in flight when it lands, the newest text is sent again behind it.
- **Unsaving a story with a note asks first, wherever the unsave comes from.** The ask sits in the guest `toggle`, so the feed, Saved, a board and the story page agree; without a note it stays instant. It checks for a note after the stored data is loaded and after the open editor has written what was just typed, and a list moves its active card off the story only once the unsave really happens, so cancelling leaves everything where it was. The confirmation dialog is fetched on first use. For an account the note may not be loaded where the unsave happens (the feed), so the toggle asks the server for the save first; if that lookup fails, it asks with neutral wording ("This story may have a note. Remove it anyway?"), since removing a note nobody could look up is the loss the question exists to prevent; a second press while the lookup is out is ignored, and `onUnsave` still runs only on a real unsave.
- **A note is written into the digest as its author wrote it, quoted line by line, and the digest weeks are ISO weeks in UTC, listed oldest save first.** Titles, tags and the collection name are escaped, so they can't break the Markdown, but a note is the reader's own Markdown: the quote keeps an open code fence or a heading in it from reaching the entries after it. The week picker offers the current week and the 7 before it; a board's digest is limited to its collection.
- **The notes slot, the `n` shortcut and the export button load after first load (`next/dynamic`, `ssr: false`), and the editor and `react-markdown` on first open.** Without it `/saved` and `/collections/[slug]` went over their ceilings; `react-markdown` is on the size check's forbidden list.
- **A note is saved 800 ms after the last keystroke, on blur and on unmount, and written synchronously when the page is closing (`pagehide`); a page that only turns hidden writes through the queue.** The editor loads the writer when it opens, so `pagehide` can send its request without waiting for a chunk; a hidden page may come back, so it keeps the order of earlier writes. Still lost: keystrokes of a tab the browser kills without either event, and a reload within the moments the writer is still loading.
- **Two tabs: the last write wins, and an open editor does not refresh from another tab.** A guest store belongs to one person on one device and the [PRD](docs/prd.md) puts collaborative editing out of scope for Phase 3, so merging two tabs' edits to one note would be machinery for a case that costs the writer a few words.
- **The landing's example briefings come from `GET /copilot/examples` at build and revalidation; "none" and a failed first build fall back to the shared sample fixture, a failed revalidation throws.** A reachable API that returns no stored briefing gets the fixture as the first question with the "Sample data" label at any time, because the API's answer is the truth; an unreachable API fills the fixture only at build or in dev, like the stories, so ISR keeps the last good page. The fixture is one briefing, so the sample page shows one tab. With the copilot flag off the loader neither fetches nor embeds anything.
- **The example section's live tabs and the renderer load through `React.lazy` when the section is within 300 px of the viewport, and the hero's briefing branch when "Briefing" is pressed.** The tabs and a skeleton are server-rendered in a panel of fixed height with its own scroll, and an observer island swaps in the live tabs, so the swap moves nothing; a tab focused, clicked or arrowed to before the swap carries over, with focus. Keeping the tabs, `next/dynamic`'s runtime and the hero switch in the first load measured `/` at 161.3 KB against 160; `React.lazy` needs no extra runtime, and `LazyBriefingView` still wraps the renderer inside the lazy chunks.
- **The hero's Feed | Briefing switch is a pair of toggle buttons (`aria-pressed`), the example section's question switch is a real tablist.** The hero switch swaps what the window shows, like the feed's sort toggle; the section's three questions are a tab set with roving tabindex, arrows, Home and End.
- **The landing `/` first-load budget is 165 KB, up from 160.** What is left after lazy loading is structural (island loader, hero switch, keycap, and module-id widening from Recharts and A2UI, about 0.1-1.4 KB on every route), and the branch measured 159.997 KB; PRD §8.5 changes in #134.
- **For a guest, the digest covers every save looked up at page load; for an account it reads the saves list page by page until a page reaches back before the chosen week.** A signed-in page may have loaded only its first saves. Saves come newest first, so the read stops at the first page that ends before the week starts, and a long history costs one request per page of the weeks since.
- **A merge fills requests under a body budget with saves and preferences first, then whole boards, then notes; the device releases what each confirmed request carried.** The limit is 512 KB and the merge is idempotent, so splitting is safe; the budget, the note count and the limit are constants in `packages/shared` that the contract and the API body limit use too. Requests are measured in UTF-8 bytes of the JSON (a note can be 3 bytes a character), the first one included. The server matches boards by slug and appends positions per request, so a board always travels whole; one that fits no request alone stays on the device with a toast. A request that fails keeps what it carried and `pendingMerge`, so the next load sends the rest; a 400 or 413 says nothing was merged and the data is kept.
- **A confirmed merge releases every board and note it sent, those the server skipped included, except one that changed after the request was built.** A skipped note or an over-limit board would be sent and skipped again on every load; one edited meanwhile (another tab) still holds something the account lacks, and the next merge sends it again. A note whose story is no longer in the saves is still sent, since an earlier confirmed request removed the saves first; the server saves the story for it. A skipped note loses its local text, the open question of [#99](https://github.com/soheilaghayour/dev-brief/issues/99) (Q8). Recovering a skipped note or board would need the skipped ids in the contract; that is the owner's decision.
- **The synced toast counts what arrived, "3 saved stories, 2 collections and 1 note synced", with zero parts left out and the singular for one; what the server skipped gets a toast of its own.** `skipped.saves` counts unknown stories across saves, board items and notes, so no toast words it as skipped saves. A skipped note, collections past 50 and stories past 500 in a board each say which limit they hit. The web sends boards and notes only while its collections flag is on, so with the flag off they stay on the device.
- **Signing out first finishes the merge, and asks before it removes data the account lacks.** It joins a merge in flight, retries once when `pendingMerge` is still set, and if the device still holds saves, boards or notes the account lacks, a dialog says how many ("2 collections and 1 note haven't synced to your account yet. Signing out will remove them from this device.") with "Stay signed in" as the default and "Sign out anyway". Only the latter empties the store, so AC-1.5.8 holds after a confirm. Sign-out and account deletion also drop the cached collections.
- **The tokens §7.1 leaves open are warm-hue hex values chosen to pass contrast, and all of `globals.css` is hex.** §7.1 and its exact-value test are hex, so mixing in OKLCH would leave two notations. White on `--destructive` and the dark label on its lighter dark value both reach 4.5:1. Success and warning colour dots, borders and tints, so they have no foreground. The values are in `apps/web/src/app/globals.css`.
- **`--accent` is lighter than the surface in both themes.** `--primary` on `--card` is only 4.52:1 in light mode, so a darker hover surface would push link text under 4.5:1; the values are in `apps/web/src/app/globals.css`.
- **The chart hues are blue, olive, purple, ochre and rose in both themes, none within the terracotta hue.** Each reaches 3:1 on the background and on cards, and a chart line never reads as a link or a button. The dash patterns above still separate the lines without colour. The values are in `apps/web/src/app/globals.css`.
- **`--brand` is used only for non-text marks and 24 px text.** `--primary` stays for links, button fills and the focus ring, because `--brand` on the background is under 4.5:1 in light mode.

## Rejected and left-out approaches

- **Fastify, Drizzle:** Express (Nest's default) and Prisma are what job ads ask for.
- **Lucia:** deprecated; Better Auth with its Prisma adapter replaces it.
- **Vercel, Railway, Render:** one Hetzner VPS with Coolify runs the always-on API (cron, SSE) at a fixed few euros a month ([§4.1](docs/prd.md#41-system-diagram)).
- **Supabase:** Postgres runs as a container on the same VPS.
- **Embeddings and vector search:** tags, full-text search, `pg_trgm` and the clustering model's same-story decision cover the need. They are reconsidered only if clustering misses its accuracy target ([§1.7](docs/prd.md#17-non-goals-all-phases), O1). Embedding each story costs about 150 tokens × 400 stories a day ≈ 60k tokens a day: around $0.001 a day on a hosted small model (list prices unverified), or about 20 ms a story on a local MiniLM-class model. It would need a schema change (a vector column or pgvector), a provider and key or a local runtime, a backfill and recorded embeddings. It stays rejected while the pre-filter meets its gates.
- **Deterministic-only clustering (a weighted score over a fixed threshold):** the owner judged score-only matching too weak, so its signals now only pre-filter candidates for the model ([F2.1](docs/prd.md#f21-clustering-ai-assisted), O1).
- **A clustering call for every new story:** most stories have no plausible duplicate, so the pre-filter's floor skips the call, and the spend stays inside the $0.02 cluster cap.
- **Gemini Flash, Flash-Lite or Hydrogen, or DeepSeek, in place of Claude Haiku 5.5:** at about 1,800 input and 240 output tokens a summary, official prices on 2026-11-21 give Haiku $0.00030 a summary, DeepSeek flash $0.00041 off-peak and $0.00083 at peak, Gemini 3.5 Flash-Lite $0.00114, Gemini 3.8 Flash $0.00225 (an introductory price, $0.0045 from 2027-01-01) and Gemini 4 Hydrogen $0.0045. Each costs more per call. Gemini's free tier also trains on the data sent and DeepSeek processes it in China, which the privacy page would have to disclose ([§8.6](docs/prd.md#86-security-basics)).
- **Email/password sign-in:** GitHub and Google OAuth only ([AC-1.5.1](docs/prd.md#f15-auth-account-saves-and-merge)).
- **Email digests:** the weekly digest is a Markdown download or clipboard copy ([AC-3.4.4](docs/prd.md#f34-collections-notes-and-digest)).
- **JIT off globally (`-c jit=off`):** it hides the symptom of a plan that scores the whole Top window; the two-stream query removes the cause.
- **A separate worker process, queues, Redis:** one API process serves REST, SSE and cron ([§1.5](docs/prd.md#15-product-principles)).
- **An A2UI adapter layer or in-house fallback renderer:** `@a2ui/react` is pinned to an exact version and upgraded like any dependency.
- **GitHub star velocity (daily star snapshots):** "new repos by stars" is the agreed proxy until [O3](docs/prd.md#34-open-items) is decided.
- **LLM tagging in Phase 1:** the deterministic taxonomy is pure and testable ([Appendix A](docs/prd.md#appendix-a--tag-taxonomy-v1)); LLM tags are an optional Phase 2 add-on (F2.7).
