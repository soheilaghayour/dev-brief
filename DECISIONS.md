# Decisions

Judgment calls in force. Requirements live in [`docs/prd.md`](docs/prd.md); this file
links to them instead of restating them.

## Decisions

- **When two tools fit, pick the one German product-startup job ads ask for.** DevBrief is a portfolio piece; every extra piece of complexity needs a stated reason, here or in the PRD.
- **GitHub Issues are the backlog.** One home for planned work; a `backlog.md` would copy it and drift.
- **`CLAUDE.md` is the one home for agent rules; `AGENTS.md` only points to it.** PRD §4.2 asks for both files; two copies of the same rules drift apart.
- **`@/*` maps to `src/*` inside each app, and `packages/shared` is imported as `@devbrief/shared`.** The PRD names neither; one import style in both apps keeps moves cheap.
- **RSS items with a missing or unparseable date are skipped.** F1.2 doesn't cover the case, and substituting the fetch time would rank old posts as fresh.
- **Node 26 (the current Active LTS) and pnpm 12, pinned in `.nvmrc` and `packageManager`.** Tooling versions come from one place each; CI reads both.
- **Nest 12 is ESM-only, so the API and `packages/shared` are ES modules with `.js` import specifiers.** One module system across the repo; the web app is bundled by Next.
- **TypeScript stays on 6.0.x.** `typescript-eslint` doesn't support 7 yet; raise it when it does.
- **The `zod` advisory GHSA-mrhx-c7xc-m3w5 is ignored in `pnpm audit`; every request-input `z.array()` gets `.max()`.** Only 4.6.6 fixes it, and the PRD pins Zod 3.25 for `@a2ui/react` ([§4.1](docs/prd.md#41-system-diagram)); request bodies are capped at 100 KB ([§8.6](docs/prd.md#86-security-basics)). Remove the ignore when the pin lifts.
- **Prisma stays on 7.10.x.** The npm `latest` tag already points at an 8.0 release candidate; the PRD specifies Prisma 7 ([§4.2](docs/prd.md#42-monorepo-layout)).
- **`Verification` keeps the `identifier` index the Better Auth CLI generates, though PRD §5.2 omits it.** The CLI output is the authority for its models ([§5.1](docs/prd.md#51-phase-map)); the index serves its lookups by identifier.
- **`Story.searchVector` declares its generation expression as `@default(dbgenerated(...))` and its GIN index as `@@index`, though PRD [§5.2](docs/prd.md#52-prisma-schema) shows neither.** Without them Prisma sees drift against the hand-edited migration and would drop the index; CI runs `prisma migrate diff --exit-code` to keep it so.
- **`SourceItem.canonicalUrl` (indexed) stores each item's own canonical URL, though PRD [§5.2](docs/prd.md#52-prisma-schema) omits it; URL dedup matches it as well as `Story.canonicalUrl`.** A Story joined by title ([AC-1.2.5](docs/prd.md#f12-scheduled-ingestion)) keeps only its first item's URL, so a later item with a joined item's URL and a different title would otherwise create a duplicate Story.
- **Integration tests use their own database, `DATABASE_URL_TEST`.** They truncate every table, which must not wipe the dev data; migrations and tests read the same variable.
- **Uber Engineering is replaced by Shopify Engineering in the seeded RSS list.** Uber's feed URLs return 404 or 406; Shopify's `blog.atom` works and is a comparable engineering blog ([F1.2](docs/prd.md#f12-scheduled-ingestion)).
- **Local env lives in one root `.env`, loaded by `dotenv-cli` in each app's `dev` and `build` scripts; `dev` falls back to `.env.example`, so a fresh clone runs without a `.env`.** Next only reads its own folder's `.env`, and Node refuses `--env-file` in `NODE_OPTIONS`; a missing variable still fails fast at boot.
- **An `exclude` phrase vetoes a tag even when a source tag names it.** [Appendix A](docs/prd.md#appendix-a--tag-taxonomy-v1) runs excludes after source tags; a "Rust Belt" post tagged `rust` by Dev.to is still not about Rust.
- **`canonicalizeUrl` throws on a string that is not an http(s) URL.** Adapters parse upstream items with Zod and drop invalid ones ([CLAUDE.md](CLAUDE.md)); a silent fallback would let a broken URL become a dedup key.
- **`percentile` counts the item itself in its window.** The mid-rank formula in [Appendix B](docs/prd.md#appendix-b--ranking-formula) needs the item in `n`, which keeps p in (0, 1).
- **The API hand-rolls a small Zod pipe and generates OpenAPI with `zod-to-json-schema` instead of using `nestjs-zod`.** `nestjs-zod` declares peers up to Nest 11 and the API runs Nest 12; the pipe is 15 lines and `@nestjs/swagger` still serves the document.
- **The throttler counts one bucket per client IP across all routes.** The library's default key includes the route, which would turn the 120 req/min global limit into a per-route limit.
- **The Origin guard exempts the safe methods GET, HEAD and OPTIONS.** Express answers HEAD with the GET handler, and [§6.1](docs/prd.md#61-conventions)'s CSRF rule targets state-changing requests.
- **An oversized body answers 400 `VALIDATION_FAILED`.** [§6.1](docs/prd.md#61-conventions) has no 413 code and requires the status to match the code.
- **The web server's API calls carry `x-internal-token` (env `INTERNAL_API_TOKEN`) and skip the rate limit.** Server-side calls reach the API without Traefik and without `X-Forwarded-For`, so all visitors would share one 120 req/min bucket; the token is compared in constant time and the API port is not published.
- **Health is `ok` or `degraded` (a source is stale or open); a down database answers 503 `UPSTREAM_UNAVAILABLE`, so `db` is always `ok` in a 200.** [§6.2](docs/prd.md#62-rest-endpoints--phase-1) names the fields but not their values.
- **A source whose kind has no registered adapter is recorded as `skipped`, not `failed`.** The seed lists Dev.to and RSS before their adapters exist; counting them as failures would open their circuits and mark every run `partial` ([F1.2](docs/prd.md#f12-scheduled-ingestion)).
- **The overall run is `failed` only when every source that ran failed, and `skipped` when none ran; skipped sources do not count.** [§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking) defines `partial` for "one source failed"; with no source left to succeed, `partial` would hide a total outage, and an all-skipped run recorded as `success` would show green during one.
- **An adapter reports `partial` through `FetchContext.reportPartial()`, and a partial source counts as a success for its circuit and health.** It returned usable items; `partial` stays visible in its run row (the reason in `error`) and makes the overall run `partial`.
- **Any GitHub response with `x-ratelimit-remaining` below 5 marks the source run `partial`, even on the last planned page; a response without the header does not.** This is the literal reading of [AC-2.4.2](docs/prd.md#f24-github-source), and it is testable; a missing header says nothing about the limit.
- **A missing `GITHUB_TOKEN` skips the GitHub source (`skipped`, "GITHUB_TOKEN not set") instead of failing env validation.** A fresh clone runs without secrets, unauthenticated search (10 req/min) is not worth supporting, and like a kind without an adapter it must not open the circuit.
- **A GitHub repo's title is `{full_name}: {description}` cut to 140 characters with a trailing `…`; its `excerpt` stays `null`.** [F2.4](docs/prd.md#f24-github-source) sets the title; repeating the description under it on the story page would only add noise.
- **"Last successful run" for `INGEST_ON_BOOT` means an overall run with status `success` or `partial`.** A partial run still refreshed the feed, so re-running at once on every restart would only hammer the sources ([AC-1.2.1](docs/prd.md#f12-scheduled-ingestion)).
- **Sources fetch in parallel but write to the database one source at a time.** Two sources inserting the same canonical URL or title at once would hit the unique constraint or split a Story; writes are cheap next to the network calls.
- **The ingestion lock is a Postgres advisory lock on its own `pg` connection, not the Prisma pool.** A session-level lock must be released on the connection that took it; it also frees itself if the process dies mid-run.
- **`pnpm --filter api ingest:once` builds the shared package and the API, then runs the compiled CLI.** tsx (esbuild) does not emit the decorator metadata Nest's injection reads, and the compiled API imports the shared package from its `dist`.
- **The HN fixtures in `apps/api/test/fixtures/hn/` are real Firebase payloads under a composed id list.** The issue's counts (100 ids, 3 jobs, 2 dead items) must be exact, so the list mixes ids recorded from `topstories`, `jobstories` and a scan of recent items.
- **A re-ingested HN item keeps the Story's first title.** Only the SourceItem title follows edits; re-tagging and title dedup stay stable for a Story.
- **The 4-min run budget covers the source fetches and the auto-summary step, not the database writes or the other post-run steps.** A hung write would hold the lock until restart; bounding it is left to the first issue that needs it. The auto-summary step fetches from three upstreams under the ingestion lock, so it checks the run's signal before each story and passes it to every fetch.
- **A source is `healthy` within 2 hours of its last success, `stale` after, and `circuit_open` while its circuit is open; `/health` and `/sources` share this one rule.** [AC-1.3.11](docs/prd.md#f13-feed-and-discovery) leaves 2-3 h undefined; one constant, `SOURCE_STALE_AFTER_HOURS`, is easy to change.
- **A source that has never finished a run (no `lastSuccessAt` and no `lastErrorAt`) is left out of `/health`, `GET /sources` and the `/stats` source count; its first failed run brings it in as `stale`.** A seeded source that can't run yet, like GitHub without `GITHUB_TOKEN`, would otherwise keep health `degraded` for good, show "1 of 13 sources behind" on every feed page, offer an always-empty sidebar filter and inflate the landing's source count. Skipped runs set neither field, while any real fetch does, so a broken source still shows. The rule is `hasCompletedRun()` in `sourceStatus.ts`.
- **The feed query selects only ids and sort keys in raw SQL; a Prisma read then loads the cards.** The keyset, tag, kind and full-text filters need `$queryRaw` ([§4.2](docs/prd.md#42-monorepo-layout)); loading sources and items through Prisma avoids hand-rolled JSON aggregation.
- **`POST /stories/lookup` drops repeated ids, keeping the first occurrence.** Order is the input order; a card twice in the result would only be noise.
- **Top keyset cursors are not snapshot-stable across a rank recompute.** A story whose score moves past the cursor may be skipped or repeated in an open scroll; the client dedups by id (AC-1.3.5) and a reload starts fresh.
- **A feed cursor is not bound to the personalisation params it was issued under; a client restarts paging when they change, keying its feed query by them.** The cursor holds only its last row's effective score and id, and other boosts give another order, so carrying it over would skip or repeat stories; checking the params would put them in every cursor for a case the client avoids.
- **Health is never cached and the API version comes from `APP_VERSION` (default `dev`).** A cached health answer would hide an outage.
- **An RSS adapter hands its etag and Last-Modified to the engine, which stores them on the Source after the run's items are saved.** Saving them at fetch time would let a failed write be hidden by a 304 on the next run, and the feed's items would never arrive.
- **An RSS item without a title or a usable link is dropped like one without a date; a relative link resolves against the feed URL.** F1.2 names neither case; a Story needs a title and an http(s) URL, and a feed's own address is the only base a relative link has.
- **An RSS item dated in the future is stored as published at fetch time.** Feed dates are author-written; a future date would otherwise keep the item at maximum freshness until that date.
- **An Atom entry's `<id>` is its guid, so `externalId = sha1(guid ?? id ?? link)`.** `<id>` is Atom's permanent identifier, unlike a link that can change scheme or path.
- **Markup-like text in a feed title or excerpt is stripped as HTML, while `a < b` stays.** §8.6 says all HTML is stripped, so an escaped `<Suspense>` goes too; only a `<` followed by a letter, `/` or `!` starts a tag.

- **Better Auth is pinned to 1.7.26 and gets Zod 4 through a scoped pnpm override.** Every maintained Better Auth line (1.3 and later) is written against the Zod 4 API and crashes on the workspace's Zod 3.25 pin ([CLAUDE.md](CLAUDE.md) item 21); the override covers only `better-auth`, `@better-auth/core` and `better-call`, so app code and the web bundle stay on Zod 3.
- **`effect` is overridden to ^3.22.1 under `@prisma/config`.** Better Auth's Prisma adapter brings the Prisma CLI into the production dependency graph, and the 3.20 it pins has the high advisory GHSA-7589-6fvf-x4pw; 3.22 is a compatible minor.
- **`/api/auth/*` is limited by a small Express middleware, not Better Auth's limiter, and has no internal-token bypass.** Better Auth either trusts a single-value `X-Forwarded-For` or needs the proxy's CIDR list; the middleware counts all auth paths together on Express's one-hop `req.ip` ([§8.6](docs/prd.md#86-security-basics)), and the web server never calls `/api/auth` server-side.
- **Better Auth's IP tracking is off.** It would store the raw client IP in every Session row, which [§8.6](docs/prd.md#86-security-basics) forbids; nothing reads the column.
- **A new user or a linked account needs an email the provider marks verified (GitHub: the verified primary email; Google: `email_verified`).** `trustedProviders` makes Better Auth skip that check when linking, so a `validateUserInfo` gate enforces [AC-1.5.3](docs/prd.md#f15-auth-account-saves-and-merge)'s "verified"; refusing unverified sign-ups too stops a stranger from squatting an email before its owner signs in.
- **GitHub requests only `user:email` (`disableDefaultScope`).** Better Auth adds `read:user` by default; `/user` returns the public profile without it ([§8.6](docs/prd.md#86-security-basics)).
- **Better Auth's origin and CSRF checks are switched on explicitly, and OAuth tokens are stored encrypted.** It turns both checks off whenever `NODE_ENV=test` or `TEST` is set; the app never uses provider tokens after sign-in, so a leaked row must not hold usable ones.
- **The test-mode sign-in route is a Better Auth plugin, registered only when `AUTH_TEST_MODE=true`, and that flag also needs a loopback `APP_URL`.** With the flag off the route does not exist (404); an unset `NODE_ENV` defaults to `development`, so the public origin is the check no environment mix-up can fake. The plugin creates the session through Better Auth's own cookie code, so tests exercise the real cookie settings.

- **Geist comes from `next/font/google`, not the `geist` package.** It self-hosts a Latin-only subset with `display: swap` as [§7.1](docs/prd.md#71-design-references-and-system) asks; the package ships every weight and subset unsplit. The build needs network access to fetch the font once. next/font's metric-matched fallback is `local(Arial)` only, which Linux and Android lack, so `globals.css` adds Liberation Sans/Arimo and Roboto fallback faces with the same overrides; without them the landing text reflows when Geist swaps in (CLS 0.23 on the CI runner, ≈0.08 on Android).
- **The shortcuts help dialog loads on first `?`.** The root layout wraps every page, and the landing budget ([§8.5](docs/prd.md#85-performance-budgets)) can't carry Radix Dialog for a dialog most visitors never open.
- **The landing page downloads Sonner only when a toast is pending.** Only someone who just deleted an account sees a toast there ([AC-1.6.2](docs/prd.md#f16-settings)), so every other visitor would download Sonner for nothing. The delete-account dialog queues its toast in `sessionStorage`, with a memory fallback, and the marketing layout's `PendingToast` loads the Toaster after the redirect. Memory alone would cover a client-side navigation, but storage also survives the full page load Next falls back to when a deploy lands mid-session.
- **The sidebar has Feed and Saved, plus Radar behind its flag; Collections arrives with its P3 issue.** Collections has no index route in [§7.2](docs/prd.md#72-routes-and-views), so a `g c` link would point nowhere.
- **E2E runs as the last steps of the `check` job, not as a second job.** One required check, and install, build and Postgres run once; the smoke tests need the built apps and a seeded database, which `check` already has.
- **The first-load JS budgets are measured from the build, not the original 90 KB.** Next 16 and React 19 alone weigh ≈135 KB gzip, so 90 KB can't be met by any code change. Each ceiling is the measured size rounded up to the next 5 KB, kept in `apps/web/bundle-budgets.json` and listed in [§8.5](docs/prd.md#85-performance-budgets). What keeps the numbers there: Zod, Radix, Sonner, the account menu and the hotkey bindings load after first paint; TanStack Query lives in the `(app)` layout, so the landing page does not carry it; the error boundaries use a dependency-free `BareButton`. Sentry's build step adds a debug-ID snippet to every chunk (≈2.4 KB per route); turning off `sourcemaps` would remove it, but client stack traces would no longer be symbolicated, so it stays. tailwind-merge (≈8.5 KB) is the price of the design system: the header toggle and the reused `StoryCard` need `ui/Button`, and the marketing layout alone measures ≈152 KB. Lighthouse ≥ 95 on the landing page is the primary gate. The Phase 2 owner decision raises `/feed` to 200 KB and `/story/[id]` to 195 KB (`/` and `/saved` keep 160 and 190), 10 KB of headroom for the features the PRD places on those pages: F2.5's follow/mute menu, F2.3's summary badge and `u` shortcut, and later F2.1's clustering. A feature PR must not raise a budget on its own.
- **The size gate is a script over the build output, not `size-limit`.** `size-limit` measures a bundle entry, not the scripts a route's HTML loads, which is what [§8.5](docs/prd.md#85-performance-budgets) defines. `apps/web/scripts/checkBundleBudgets.mjs` sums the gzip of the route's scripts (the HTML for prerendered routes; the build manifests, which list the same files, for server-rendered ones) against `apps/web/bundle-budgets.json`. Before measuring, the gate checks that the manifest rule reproduces the HTML of the prerendered `/saved` (same route group), so a Next upgrade or a new `(app)` boundary file cannot make it under-count silently.
- **Mobile navigation and mobile filters are two separate sheets, both loaded on first open.** The menu opens a left drawer with the navigation; filters open a bottom sheet (AC-1.3.12), so the filter UI is rendered once per breakpoint and never inside the drawer.
- **The shortcut registry treats a sequence's first key as pending for 1 s.** A plain single-key shortcut does not run in that window, so `g` then `s` (go to Saved) never also fires `s` (save).
- **The rank recompute loads the 7-day window into memory and writes it in transactions of 500 updates through Prisma.** About 3k stories plus their items fit comfortably; raw bulk SQL would break the principle that raw SQL appears only where the Prisma client can't say the query ([§4.2](docs/prd.md#42-monorepo-layout), and the `$queryRaw` decision below).
- **The daily `TagDailyStat` window is today plus the two UTC days before it, and a story counts once per tag on its UTC publish day.** [AC-1.7.3](docs/prd.md#f17-platform) says "last 3 UTC days" without saying whether today counts; including it lets `count7d` in `GET /tags`, which sums the 7 UTC days ending today, count today's stories. Today's row stays partial until the next ingestion run or the daily job recomputes it.
- **Radar "Top movers" sort by absolute change `|current − previous|`, then slug, and `deltaPct` is `null` ("new") when the previous window is 0.** This reproduces the [§7.3](docs/prd.md#73-wireframes) wireframe order, and sorting by percentage would put "1 → 3 = +200%" above real movement.
- **The radar's "engagement" is the raw sum of `TagDailyStat.engagementSum`, which mixes HN points, Dev.to reactions and GitHub stars on their own scales.** [AC-1.7.3](docs/prd.md#f17-platform) stores no normalised figure per tag; a percentile-weighted count (`storyCount × avgPercentile`) is the alternative if the mix proves misleading.
- **Both radar windows end on yesterday (UTC), the last complete day, and an ingestion post-run step recomputes `TagDailyStat` for yesterday and today.** Comparing a partial today against full days made every steady tag look like it was falling (about −13% all day, −27% before 03:15 UTC), because the daily job is the only other writer. The post-run step keeps yesterday's row complete soon after midnight; the 03:15 job still rolls up three days. Today's row is never read by the radar.
- **`NuqsAdapter` lives in the `(app)` layout, not the root layout.** The landing page must not ship nuqs; the feed and story pages are dynamic on their own (`searchParams`, a dynamic segment), and Saved stays static.
- **Next's `/api/*` rewrite exists only when the build-time env `API_PROXY_URL` is set.** `next dev` and the e2e build set it; production builds leave it unset because the real proxy routes `/api/*`, and `typecheck` and `build` need no env.
- **Web code loads `lib/api/endpoints` on first use (`import()` inside the query functions) and `@devbrief/shared` is `sideEffects: false`.** Together they keep Zod and every contract out of first-load JS. The limits the web needs from the feed contract live in `contracts/feedLimits.ts`, apart from the schemas, because importing a constant from a module that builds Zod schemas pulls Zod in.
- **The search, sort and filter slots render on `/feed` only, and the mobile "Filters (n)" bar is a slot of the shell.** On Saved and Story they would edit URL params that page does not read.
- **The e2e seed replaces all stories and saves, resets every source to healthy with its circuit closed, and uses fixed story ids.** Health dots and `focus` deep links are then deterministic. It refuses to run unless the database name ends in `_test` or `e2e`, or `ALLOW_DESTRUCTIVE_SEED=1` (CI sets it); it lives in `apps/api/prisma/seedE2e.ts`.
- **Filter changes use nuqs' shallow `history.replaceState`, not `router.replace`.** A non-shallow replace would re-run the dynamic feed page on the server and prefetch twice; the URL stays the single source of truth.
- **The server prefetch for `/feed` never retries, and the search input stops at 100 characters.** A failing API must not delay the HTML by the retry back-off (the browser retries), and the contract's `q` maximum is 100, so the UI can't produce a 400.
- **Playwright sends `x-internal-token` on every browser request.** One test run is one visitor, so the per-IP limiter is not exercised by e2e.
- **A guest can keep 500 saves, and a full list refuses new ones with a toast instead of dropping old ones.** 500 is what one `POST /me/merge` accepts ([§6.2](docs/prd.md#62-rest-endpoints--phase-1)), so every local save can reach the account; silently evicting a save would lose data the guest chose to keep.
- **The "Saved on this device" toast and the storage-unavailable warning each show once per tab session, tracked in `sessionStorage` with a memory fallback.** [AC-1.4.1](docs/prd.md#f14-guest-saves) and [AC-1.4.4](docs/prd.md#f14-guest-saves) say "once" without defining the scope; when storage is unavailable, the warning replaces the first save toast.
- **`/saved` fixes its list of ids when it first shows; saves made there change what is shown but trigger no new lookup.** Unsaving a card removes it at once and moves the active card to its neighbour; a re-save happens in the feed.
- **The guest hint is a fixed banner at the bottom of the screen, shown to guests only.** It appears after hydration, so in the page flow it would push the feed down ([AC-1.3.9](docs/prd.md#f13-feed-and-story-page) holds CLS under 0.05); a signed-in user never sees guest copy.
- **Open tabs follow each other through the `storage` event, and every save re-reads storage before changing it.** Each tab would otherwise write its whole list over the other's.
- **Guest data written by a newer app version is left untouched: the store runs in memory instead.** After a rollback, overwriting it with the older shape would erase saves.
- **`merged.saves` counts the distinct existing stories in a merge request, whether or not they changed a row; `skipped.saves` is the number of unknown story ids.** [§6.2](docs/prd.md#62-rest-endpoints) doesn't define the two counts; this keeps a repeated merge answering the same and makes the "N saved stories synced" toast ([AC-1.5.5](docs/prd.md#f15-auth-account-saves-and-merge)) count what the user now has in the account.
- **The synced toast reads "1 saved story synced" for one save, and nothing shows when no story was merged.** [AC-1.5.5](docs/prd.md#f15-auth-account-saves-and-merge) words only the plural; "1 saved stories" reads as an error.
- **The device releases every save it sent once the server confirms, unknown stories included.** A story the server doesn't know is gone for good; keeping it would resend it on every load.
- **A signed-in load merges whenever the device holds saves or preferences; `pendingMerge` only records an attempt the server hasn't confirmed, and it joins the v1 guest store without a version bump.** It is set before the request and cleared on the server's answer, so a tab that dies mid-request still counts as a failed attempt; stored v1 data without the field reads as `false`, so the `devbrief:guest:v1` key and the `version: 1` shape of [AC-1.4.2](docs/prd.md#f14-guest-saves) stay.
- **Per-user limits (merge 10/min, mutations 60/min) use a small guard after `AuthGuard` instead of `@nestjs/throttler`.** The global throttler runs before `AuthGuard`, so it can't key on the user; a second `ThrottlerGuard` would still need its own tracker and storage for two buckets ([§8.6](docs/prd.md#86-security-basics)).
- **While `GET /me` is pending, `useSaves()` and `usePreferences()` are not ready and changes go to the device store.** A guest's first save or mute never waits on the network, and a change made before sign-in is recognised is picked up by the merge.

- **Nothing in the repo hard-codes the production domain; every URL comes from `APP_URL` and its siblings, and docs use `devbrief.example`.** The domain is not bought ([O2](docs/prd.md#34-open-items)).
- **Production is two Coolify Dockerfile applications plus a Coolify-managed Postgres, not a compose file.** Coolify's scheduled S3 backup (AC-1.7.7) exists only for its own database resources, and one application per image gives each its own health-checked rolling deploy.
- **The api image runs `prisma migrate deploy` as its start command rather than as a separate release step.** A non-zero exit keeps the new container unhealthy, so Coolify's rolling update leaves the old one serving (AC-1.7.5) with no extra Coolify configuration; two instances overlapping briefly is safe because `migrate deploy` takes an advisory lock. `prisma` therefore moves from devDependencies to dependencies.
- **The api image is built with `pnpm deploy --prod --ignore-scripts` and seeded by the compiled `dist/cli/seed.js`.** The `postinstall` hook needs dev tooling, and the image has no `tsx`, so the seed lives in `src/cli/` where the compiled build includes it. The Prisma schema engine is fetched at image build time instead, so a deploy never downloads it. `prisma` joins the runtime dependencies, which makes the image large (about 450 MB of `node_modules`); one VPS can afford it.
- **CI builds both images on every PR and pushes nothing.** Coolify builds on the VPS from the pushed commit, so a registry would add a credential and a hop for no benefit.
- **The release for Sentry and `/health` is Coolify's `SOURCE_COMMIT`, taken as a Dockerfile build argument, `unknown` when unset.** It changes per deploy without anyone editing a variable, but Coolify passes it to builds only with "Available during build" on, so the runbook sets it and the production smoke rejects `unknown`.
- **Sentry events are scrubbed in `beforeSend`, not by `sendDefaultPii` alone.** On 10.x that flag still leaves the session cookie, `authorization` and `x-internal-token` on server error events, so one shared scrub drops them and client IPs ([§8.6](docs/prd.md#86-security-basics)).
- **The api uploads no source maps to Sentry.** It runs from compiled `dist/` without maps, and shipping them in the image would expose the source for little gain at this size; web maps are uploaded and deleted.
- **Both containers use their image's `HEALTHCHECK` (Node `fetch`), with Coolify's dashboard health check off.** The dashboard check needs `curl` or `wget` in the image, which would add a package to both runtimes for the same result.
- **Sentry is pinned to the 10.x line.** 11.x removed `sendDefaultPii`, which [AC-1.7.6](docs/prd.md#f17-platform) names; revisit when the criterion is reworded.
- **The browser Sentry SDK loads by dynamic import after the page, and errors thrown before it loads are not reported.** Statically imported it adds tens of KB to first-load JS, which the [§8.5](docs/prd.md#85-performance-budgets) budgets cannot carry.

- **The badge "context menu" is a dropdown opened by click, Enter or Space, not a right-click menu.** A right-click menu can't be reached by keyboard or on touch screens ([§7.1](docs/prd.md#71-design-references-and-system) sets WCAG AA).
- **Every tag and source badge opens Follow / Mute, on the feed, Saved and the story page; the landing preview's badges stay plain.** The preview is static and shows the same stories to everyone, so it ignores preferences. The pages pass the menu to their badges, so the landing page doesn't load it, and the dropdown's code loads on first open.
- **A signed-in visitor's first page is rendered with their preferences; a guest's muted cards leave at hydration.** The server forwards the session cookie, reads the account's preferences and asks the feed for the page they give, so a muted story is never in the HTML. It can't read a guest's `localStorage`, so a guest's server-rendered page can show a muted card until the page hydrates; then the stored mutes are read synchronously and the card is gone before the next paint, and the page stays filtered while the personalised one loads. A skeleton in place of the rendered page would cost more than that one flash ([AC-2.5.2](docs/prd.md#f25-followmute)).
- **Feed params from preferences stay out of the URL and join only the request and the `['feed', …]` key.** The URL holds the filters chosen for this view; preferences are standing personal state, and a shared link must not carry them.
- **Settings names a preferred source by its name from `GET /sources`, and by its slug once the source list no longer has it.** A removed source stays a valid preference (format-checked slugs, above), so the user can still see and remove it.

- **Dev.to text comes from one extra `GET /api/articles/{id}` call per summarised story, for its first Dev.to item.** [F2.3](docs/prd.md#f23-ai-summaries) asks for `body_markdown`, which the list endpoint doesn't return; [§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking) counts it with the comment calls of each attempt, failed attempts included.
- **A failed comment or article fetch aborts the summary instead of summarising partial input.** A summary is cached forever, so one built from half the discussion would never be corrected.
- **Auto candidates come from the 7-day Top window.** Older stories keep a frozen `rankScore` ([Appendix B](docs/prd.md#appendix-b--ranking-formula)) and never appear in Top.
- **Auto summaries need `AUTO_SUMMARIES=true` as well as `FEATURE_SUMMARIES=true`; it defaults to `false`.** CI's e2e API runs with summaries on and a placeholder key, so the ingestion run after boot or the hourly cron would otherwise make live LLM calls there; defaulting off fails safe, and production sets both.
- **Clustering needs `AUTO_CLUSTERING=true` as well as `FEATURE_CLUSTERS=true`; it defaults to `false`.** Same reason as `AUTO_SUMMARIES`: a key and the feature flag alone must not start spending on every ingestion run, so the live calls have a switch of their own that defaults to off and that production sets with the flag.
- **The step finds a run's new stories by `firstSeenAt` at or after `PostRunContext.startedAt`, which the engine reads from the database clock (`SELECT now()`).** The run's overall `IngestionRun` row is written after the post-run steps, so it can't bound the new stories, and `firstSeenAt` defaults to the database clock, so an API host whose clock runs ahead or behind would otherwise miss stories or decide them twice.
- **A new story is matched only against stories that were decided before it.** The pool leaves out the run's not-yet-decided new stories, so no story is paired by an earlier story's decision and then decided again (F2.1: S is single when decided).
- **A run makes at most 100 clustering calls, and the step ends after 3 unexpected errors in a row; one unexpected error on its own leaves that story single and the step goes on.** The cap keeps the run's 4-minute budget shared with the auto summaries; the rest of a first run's backlog stays single, like any capped decision. Three database errors in a row mean the database is down, which a fourth story would not fix.
- **`sameLink` is true for the same GitHub repo (any path inside it), or for the same host without `www.` where one path is a segment-wise prefix of the other and the shorter path isn't `/`; equal paths need equal queries.** On hosts that carry many projects (github.com, dev.to, medium.com, youtube.com and their subdomains such as `m.youtube.com`) only the repo rule applies, since a shared host there says nothing, and `watch?v=a` is not `watch?v=b`. Entity tokens take no host at all: two posts of one blog are not duplicates.
- **A query Prisma can't express is a parameterised `$queryRaw` tagged template; every other query uses the Prisma client.** The cases are the feed query (FTS, dynamic ORDER BY, keyset cursor) and reading the database clock; the one principle is that raw SQL appears only where the client can't say it, and never as built strings.
- **Candidate scoring computes the trigram similarity of `pg_trgm` in TypeScript, over a pool loaded once per run, instead of calling `similarity()` per new story.** At the production-sized window (1,200 stories, 400 new) the per-story `similarity()` query ran ≈560k comparisons as a sequential scan and, with the entity tokens recomputed per row, took ≈19.6 s against the 5 s of [AC-2.1.2](docs/prd.md#f21-clustering-ai-assisted); scoring in memory takes ≈1.2 s. The score is the same number (Jaccard over padded trigrams), and a test compares it with `similarity()` for every pair of fixture titles. The trigram index from the migration is then unused by the step; it stays because the migration is applied.
- **`CLUSTER_CANDIDATE_MIN_SCORE` is 0.20, not the PRD's starting 0.25, and a patch version also counts as its release line.** On the main fixture 0.25 passes 23 of the 25 positive pairs (92%, under the 95% gate) and 0.20 passes 24 (96%); "26.5.0" and "26.5" share a token, and "SQLite 4" is read as 4.0 only against the same name. The held-out pairs, taken from the recorded snapshots and labelled before the pre-filter saw them, pass 1 of 4 positives: real cross-source posts are worded far apart, so the floor misses most of them, and the constants are not tuned on that set. The floor only decides whether a call is worth making.
- **Clustering doesn't launch while `clusterMatch.v1.pairs.json` holds `"placeholder": true`.** A hand-written reply proves nothing about the model, so the precision and recall assertion (AC-2.1.1) skips with a warning and doesn't count as passing; the owner records the real replies in [#82](https://github.com/soheilaghayour/dev-brief/issues/82) before `FEATURE_CLUSTERS` goes on in production.
- **A string with a URL or markup fails the LLM schema, which triggers the one retry; a URL is a scheme, `www.`, or a domain with a common TLD followed by a path.** [§8.2](docs/prd.md#82-prompting-and-llm-safety) says the model can't emit URLs or HTML, so the schema enforces it. The TLD list keeps names like "Node.js/Deno" valid text.
- **`hasSummary` and `summary` are omitted, not `false`/`null`, while `FEATURE_SUMMARIES` is off.** That keeps flag-off responses identical to Phase 1.
- **Prompts live in `apps/api/src/modules/llm/prompts/` as §8.2 says, although only the summaries module uses this one.** Phase 3 adds the copilot prompt beside it.
- **The §8.1 input budget counts what the ledger estimates: system prompt, JSON schema and title together ≤ 600 tokens, and the text and comment budgets include their `<source>` delimiters.** `LlmService` reserves `ceil(UTF-8 bytes / 2)` over all of it, so only then is a summary's worst case the $0.00075 the 20-a-day auto cap is sized for. The title is cut at 64 tokens and the system prompt kept terse to fit; the provider strips length and count limits from the schema it sends, so the prompt states them.
- **Comments alternate between a story's threads at each depth, and a comment that doesn't fit the budget is skipped, not the end of the list.** One long HN thread would otherwise push every Dev.to comment out, and one long top comment would crowd out all the shorter ones after it.
- **A Dev.to Markdown body loses its front matter, Liquid embeds, images and link targets before it is converted like HTML.** They carry no words to summarise, and URLs in the input invite URLs in the output, which fails the schema.
- **Post-run steps run in a fixed order (`clustering`, `rank-recompute`, `auto-summaries`, then `feed-cache-clear`), not in registration order.** [§4.3.1](docs/prd.md#431-ingestion-pipeline-hourly) orders them, and Nest's module init order is not a contract. Clustering comes first so the recompute ranks the new clusters; that needs the cluster rank upkeep of the cluster feed issue (#79), which merges before or together with the clustering step. The cache clear is a step of its own, so it also follows the new summaries, and the engine runs it even when an earlier step failed.
- **HN Algolia responses may be up to 10 MB, not the 2 MB `HttpClient` default.** The most-discussed threads, the ones auto summaries pick, run to several MB.
- **Every Dev.to request of the process goes through one `DevtoClient` (`common/devto`): ingestion's list calls and all summaries share its serial queue, with the 2.5 s gap from the end of one request to the start of the next; at most 4 HN Algolia requests are in flight across all summaries.** [§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking) sets both limits per client, and on-demand summaries can run while an ingestion run does. The client is also the one home of the 429 rule: `Retry-After` is honoured up to 30 s; past that, or without one, the request fails and its caller aborts the source.
- **The auto step stops for the run on a spent cap, a provider error or an upstream failure (5xx, 429, timeout, lost connection), skips to the next story only on invalid or refused output or that story's 404 or malformed payload, and tries at most 25 stories per run.** A revoked key, an outage or a throttle would fail every following story too, and a provider 4xx is billed at $0, so the spend cap alone would never stop the loop. The 25 stories also bound a run of Dev.to-only candidates; the per-run HN Algolia budget of [§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking) is counted in requests (see the HN Algolia entry below).
- **A story whose auto call failed today (a `failed` `summary_auto` ledger row with its id as `refId`) is not tried again until the next UTC day; with clusters on, its cluster is not either.** The same input would most likely fail the same way, and each try costs the run an attempt; the ledger already holds the fact, so no schema change is needed. The cluster is the key because a rank recompute can move the representative, and the retry would repeat the same failure.
- **The auto step counts HN Algolia requests, not attempts: one per HN item of each tried story (of every cluster member), failed tries included, at most 25 per run.** A cluster can hold several HN items, so 25 stories could mean far more than the 25 requests of [§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking). A candidate that no longer fits the remaining requests is passed over and a later, smaller one may still run; a candidate found already summarised made no request and gives its share back; a cluster with more than 25 HN items is never auto-summarised (on demand still works).
- **A summary's text is the representative's Dev.to article if it has one, else the first Dev.to member's article in `rankScore` order, else the first excerpt in member order (representative first).** HN stories never have an excerpt, so the common HN-representative cluster with a Dev.to member would otherwise summarise without any article text; the PRD asks for the best available text. The article call stays one per summary ([§8.3](docs/prd.md#83-external-sources-timeouts-retries-circuit-breaking)).
- **A clustered `generate` is single-flight per cluster inside the process: the first request generates, concurrent requests for any member of that cluster await the same promise and answer `cached`.** Two members' requests would otherwise both pass the cache check and both pay for a model call. A database lock held across the fetches and the model call was rejected: it holds one pool connection per waiter, so 10 concurrent clustered generates stalled the whole API, and its transaction timeout counted the fetch and model time, so the commit failed after the call was paid. The auto step stops waiting when the run's signal aborts. Across instances (only a rolling deploy runs two) the unique `Summary.storyId` is the backstop: both write on the representative, the loser's insert hits P2002 and it returns the stored summary as `raced`, keeping its quota slot because its call was paid. Single stories, and every story with the flag off, skip the map.
- **While the prompt-injection recording holds `"placeholder": true`, its recorded-reply test (AC-2.3.7) and the estimate-versus-reported-tokens test skip with a warning, and summaries don't launch.** A hand-written reply proves nothing about the model, so tests passing on it would be invented evidence; the owner records the real one before `FEATURE_SUMMARIES` goes on ([operations](docs/operations.md#anthropic-key-and-spend-limit-phase-2)).
- **The prompt-injection reply is recorded by `apps/api/test/recordLlmFixtures.ts`, which sends the production `LlmService` call with a stand-in ledger.** It is test tooling, not a CLI the app ships, and needs no database; the recorded reply then answers exactly the request production makes.
- **A quota slot is taken before generation by a guarded increment (`updateMany` where `count < limit`) and given back on any failure and when the summary turned out to be stored already.** The limit check lives in the increment, so it can't overshoot under concurrency or reject below the real count while another request releases; a cached summary costs no quota (bite 26). The slot stays used only when a concurrent request stored the summary during this call's model request, because this call's cost is already in the ledger.
- **Guest summary quotas are keyed by IP digest plus device id, with no IP-only backstop.** That is what [AC-2.3.3](docs/prd.md#f23-ai-summaries) specifies; rotating device ids only spends the global on-demand cap ([`llm/budget.ts`](apps/api/src/modules/llm/budget.ts), [§8.1](docs/prd.md)), which bounds the cost.
- **`IP_HASH_SECRET` (32+ characters, required with `FEATURE_SUMMARIES`) drives the daily-rotating salt: `HMAC-SHA256(secret, utcDay)`.** [§8.6](docs/prd.md#86-security-basics) asks for a rotating salt without naming its source; a secret-derived salt needs no storage and survives restarts.
- **A 429 `QUOTA_EXCEEDED` sends `resetsAt` and `Retry-After`; the `RateLimit-*` headers belong to the 5/min/IP window.** [§6.1](docs/prd.md#61-conventions) names `resetsAt` for quota errors, and the filter derives `Retry-After` from it.
- **The summary panel's label says "based on N comments" from the consensus, so a summary without consensus reads "AI-generated" alone.** `StorySummary` carries the comment count only inside `consensus`, and that is `null` below 5 comments; adding a field would amend the contract for a number the "Not enough discussion yet" text already explains.
- **`u` on the feed opens the story page with `?summarize=1` and starts the summary there.** Feed cards have no room for a panel, and the result needs a place to render in place.
- **The e2e suite checks stored summaries only; generation is covered by integration and component tests.** CI never calls the live LLM, and a mock-LLM switch in the production API would be test-only code in the shipped app.
- **`hasSummary` on a cached feed page can lag a new on-demand summary by up to 60 s.** That is the feed cache TTL ([§8.4](docs/prd.md#84-caching)), and clearing it on every on-demand summary isn't worth it.
- **`INGEST_SCHEDULE` decides whether `AppModule.register(env)` imports `ScheduleModule`; unset it is on in production and off elsewhere.** Leaving the module out registers no cron at all (hourly ingestion and daily maintenance), where a guard inside each job would leave the scheduler running and prove less. Off by default in dev and test because developers run `ingest:once` by hand and a test app alive at :05 UTC would hit live sources; `createTestApp` and CI's e2e API force it off. `INGEST_ON_BOOT` is unchanged and independent. The daily job only touches the database, but it shares the module, and tests have no need of it.
- **A `Briefing` takes up to 24 children (`ChildIdList.max(24)`), because every story card is a direct child of `root` and the largest legal `BriefingPlan` (6 `stories` sections × 4 picks) compiles to 24 ([§6.4.4](docs/prd.md#644-llm-output-contract-briefingplan-compiled-to-a2ui)).** At 12, a valid plan made the `root` entry fail its schema mid-stream. Nesting the cards under a per-section container would add a seventh catalog component, and a cap on total picks can't be expressed in the JSON Schema the model is given, so the plan would fail only after it had streamed.

- **`@a2ui/react` and `@a2ui/web_core` are pinned to 0.15.0, and the renderer loads only in the browser, through `next/dynamic` with `ssr: false` ([O4](docs/prd.md#34-open-items)).** 0.15.0 is npm's `latest` (2026-11-02). It speaks A2UI v1.0: `@a2ui/web_core/v1_0` validates the four envelopes with `"version": "1.0"` and provides `MessageProcessor`, `Catalog` and `CommonSchemas`, and the root entry of `@a2ui/react` (there is no `/v1_0` subpath; `/v0_9` and `/v0_8` are the legacy ones) provides `A2uiSurface` and `createComponentImplementation`. It peers on `react ^18 || ^19` and `zod ^3.25.76`, so it runs on React 19.3, Next 16.4 and the workspace's single Zod 3.25.76. Client-only rendering is a necessity, not a choice: importing `@a2ui/react` on the server throws `HTMLElement is not defined` (it defines a custom element class at module load), and a `'use client'` component that imports it fails the build's prerender. `@a2ui/web_core/v1_0` imports cleanly on the server. The lazy chunks for a stub catalog plus the fixture are ≈ 89 KB gzip: mostly `web_core`, plus `lit` (pulled in because the root entry imports the v0.9 basic catalog's Markdown bridge) and `zod-to-json-schema`. `markdown-it` and DOMPurify are not in them. The `@a2ui/markdown-it` dependency peers on `web_core ^0.14.0`, an unmet peer that nothing loads.
- **A2UI component ids are UAX #31 identifiers (`s0_takeaways`, `s1_story_0`), and only the `Briefing` may be `root`.** A2UI v1.0 requires component ids to follow UAX #31, which excludes hyphens ([spec](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md#catalog-entity-naming-rules)), and the pinned `MessageProcessor` rejects a hyphenated id. `A2uiComponentEntrySchema` enforces both rules, so an invalid entry fails on the server before it is sent ([§6.4.3](docs/prd.md#643-devbrief-a2ui-catalog-v1)).
- **`catalog.v1.json` is the A2UI v1.0 catalog document, generated by `pnpm --filter @devbrief/shared catalog:generate`, with the catalog id as `$id` and `catalogId` and an `allowedParents` per component.** `allowedParents` is `Surface` for the `Briefing` and `Briefing` for the rest (`ALLOWED_PARENTS` in `catalog.ts`). The spec asks for both ids, and `Surface` is its name for the parent of a surface's root. The pinned `Catalog.fromJson` loads the document. A test fails when the committed file differs from the generated one.
- **pnpm overrides pin `@a2ui/markdown-it>dompurify` to `^3.4.18` and `@a2ui/react>@a2ui/web_core` to `0.15.0`.** The pinned `@a2ui/markdown-it` locks dompurify 3.4.11, which has advisories fixed in 3.4.17, and it peers on `web_core ^0.14`; one `web_core` copy keeps `MessageProcessor` and `A2uiSurface` on the same signal instances.
- **`GET /me/collections/:id` and `GET /me/saves/:storyId` exist although the first PRD draft listed no such reads.** The board shows one collection's items with their notes, and the story page edits one save's note; the paginated saves list can't serve either without loading every page ([§6.4.1](docs/prd.md#641-endpoints) rows 27 and 29).
- **A collection's slug is fixed at creation and kept on rename; `collectionSlug` (in `packages/shared`) gives ASCII words joined by hyphens (`ß`, `ø`, `æ`, `œ`, `ł`, `đ`, `þ` transliterated), `-2`, `-3` … on a clash, and `collection-<6-character hash of the name>` for a name with no ASCII word.** Board links survive a rename, the merge matches guest and account collections by slug, and the guest store needs the same slugs; the hash keeps "日本語" and "🚀🚀" from sharing one slug.
- **A user has at most 50 collections and a collection at most 500 items; a manual add over a limit answers 400 `VALIDATION_FAILED`, and the merge keeps to the same limits, reporting the overflow as `skipped.collections` and `skipped.items`.** Merged collections beyond the 50th (in request order) are not created and items beyond a collection's 500th are not added, because a merge that ended over a limit would leave an account no manual action could bring back under it; the counts let the client say so instead of dropping data silently. A merge request may not repeat a slug (400).
- **`PUT /me/collections/:id/items/:storyId` answers the updated `Collection`, and a collection item takes its `userId` from the collection's owner, never from the request.** The schema would allow an item whose `userId` differs from its collection's owner (PRD §5.2); this way an item can only point at its owner's own save, and the body carries no user.
- **Positions of collections and of a collection's items are dense, 0-based, and kept dense by bulk statements whenever one moves, is deleted or is unsaved.** A client can send "move to index n" without knowing the gaps; one range shift instead of a row-by-row rewrite keeps unsaving a story that sits on many large boards inside the transaction timeout.
- **Collection writes take a per-user advisory lock with `pg_try_advisory_xact_lock`, retry 3 times 50 ms apart, then answer 409 `CONFLICT`, which the client may retry.** Waiting on the lock would hold a database connection per waiting request and starve everyone else's reads; `CONFLICT` is a new error code because no existing one means "busy, try again".
- **An empty note (`""`) counts as no note: `PATCH` stores `null` and the merge ignores it.** One way to say "no note" keeps the editor's cleared text and a never-written note the same thing.
- **A note merge that conflicts appends the guest note after `\n\n---\n\n` unless the server note equals it or holds it as one whole `---`-separated segment; a combined note over 20,000 characters keeps the server note and counts the story in `skipped.notes`.** A repeated merge appends nothing, so the merge stays idempotent (bite 18), and whole-segment matching, unlike a substring check, does not drop a short note like "TODO" that the account note merely contains. A skipped note is lost on the device once the client confirms the merge; the alternative, keeping it on the device, needs a way to stop it being resent.
- **The merged note takes the guest note's `updatedAt` as its `noteUpdatedAt`; a note for a story the account has not saved saves the story.** The date is then a function of the request, so a repeat changes no row, and a guest note always belongs to a saved story.
- **`merged.collections` counts distinct guest slugs, `merged.notes` counts stories whose note was set or already present, and `skipped.saves` counts every unknown story id of saves, collection items and notes together (so a toast must not word it as "N saves skipped").** Each counts what was processed, whether or not it changed anything, like `merged.saves`.
- **The merge's `collections` and `notes` work with `FEATURE_COLLECTIONS` off, like `preferences`; the note fields of `Save` and the saves list are omitted while it is off.** The merge route is unflagged and the inputs are additive; omitting the fields keeps flag-off responses identical to Phase 2.

## Rejected and left-out approaches

- **Fastify, Drizzle:** Express (Nest's default) and Prisma are what job ads ask for.
- **Lucia:** deprecated; Better Auth with its Prisma adapter replaces it.
- **Vercel, Railway, Render:** one Hetzner VPS with Coolify runs the always-on API (cron, SSE) at a fixed few euros a month ([§4.1](docs/prd.md#41-system-diagram)).
- **Supabase:** Postgres runs as a container on the same VPS.
- **Embeddings and vector search:** tags, full-text search, `pg_trgm` and the clustering model's same-story decision cover the need. They are reconsidered only if clustering misses its accuracy target ([§1.7](docs/prd.md#17-non-goals-all-phases), O1).
- **Deterministic-only clustering (a weighted score over a fixed threshold):** the owner judged score-only matching too weak, so its signals now only pre-filter candidates for the model ([F2.1](docs/prd.md#f21-clustering-ai-assisted), O1).
- **A clustering call for every new story:** most stories have no plausible duplicate, so the pre-filter's floor skips the call, and the spend stays inside the $0.02 cluster cap.
- **Email/password sign-in:** GitHub and Google OAuth only ([AC-1.5.1](docs/prd.md#f15-auth-account-saves-and-merge)).
- **Email digests:** the weekly digest is a Markdown download or clipboard copy ([AC-3.4.4](docs/prd.md#f34-collections-notes-and-digest)).
- **JIT off globally (`-c jit=off`):** it hides the symptom of a plan that scores the whole Top window; the two-stream query removes the cause.
- **A separate worker process, queues, Redis:** one API process serves REST, SSE and cron ([§1.5](docs/prd.md#15-product-principles)).
- **An A2UI adapter layer or in-house fallback renderer:** `@a2ui/react` is pinned to an exact version and upgraded like any dependency.
- **GitHub star velocity (daily star snapshots):** "new repos by stars" is the agreed proxy until [O3](docs/prd.md#34-open-items) is decided.
- **LLM tagging in Phase 1:** the deterministic taxonomy is pure and testable ([Appendix A](docs/prd.md#appendix-a--tag-taxonomy-v1)); LLM tags are an optional Phase 2 add-on (F2.7).
