# Architecture

The system as built. The target design is in [`prd.md`](prd.md) §4.

Two apps and one shared package:

- `apps/web`: Next.js, served on one origin with the API.
- `apps/api`: NestJS on Express, global prefix `api/v1`.
- `packages/shared`: Zod contracts and pure core functions used by both apps.

## Feature flags

One env variable per unlaunched feature; see PRD §3.

## Landing page

`app/(marketing)/page.tsx` is static with ISR. `loadLandingData` fetches the top stories, the stats and (with the copilot on) the example briefings at build and revalidation. It keeps up to 30 stories from the last 24 h, falls back to `content/landing-fixture.json` below `PREVIEW_MIN_STORIES` fresh ones, and cuts each story with `toPreviewStory` to the fields its card renders under the page's flags before the data reaches the client.

`HeroSection` (a Server Component) lays out the hero: text left and the preview window right from `md` up, stacked below. Its dedup sentences follow the clusters flag. `HeroPreview` is the one client island above the fold. It server-renders every story of the selected chip as a compact `StoryCard` inside a frame of fixed height that scrolls on its own, the Briefing view shares the same height, and cards past the first six carry `content-visibility: auto`. Chips filter the embedded stories in the browser (`previewLogic.ts`). A click on a title opens `/story/<id>`. A cluster card shows `ClusterSourceLine` and a static "+N related" link to the same page, since the feed's expanding `RelatedToggle` needs TanStack Query, which the landing doesn't load.

## AI pipeline

`apps/api/src/modules/llm/` is the only code that calls a model. Feature modules import `LlmModule` and call `LlmService.generateStructured({ feature, schema, system, prompt, maxOutputTokens })`, which returns the validated object with its token counts and cost, or throws `SpendCapReachedError` (callers answer 503 `SPEND_CAP_REACHED`) or `GenerationFailedError` (502 `GENERATION_FAILED`).

Each call runs reserve → call → settle against the `LlmUsage` ledger (`SpendLedgerService`):

1. **Reserve.** The estimated input plus `maxOutputTokens`, priced as the call's worst case, must fit under both the feature's daily cap and the global one. The reservation inserts a `reserved` row; a refused one throws before the model is called.
2. **Call.** The Vercel AI SDK's `generateText` with `Output.object` and the Anthropic provider (`LLM_MODEL`), thinking off and effort `low`, with no SDK retries.
3. **Settle.** The row becomes `settled` at the cost of the AI SDK's `usage`, or `failed` at the usage a failure may have billed.

A retry, after invalid output or a transient provider error, is a new reserve → call → settle with its own row; `RETRY_POLICY` in `llm.service.ts` holds the rules, and [`DECISIONS.md`](../DECISIONS.md) the estimate, settle and retry rules with their reasons.

The caps, the price table and the cost math live in `llm/budget.ts`, as pure functions; env overrides each cap and the configured model's prices. Committed spend counts an open reservation at `reservedUsd` and a closed row at `costUsd`, per UTC day; `GET /health` reports the same figure as `llm.spentTodayUsd`.

Reservations are serialised per UTC day: each runs in one transaction that first takes `pg_advisory_xact_lock(<ledger key>, <UTC day number>)`, so two concurrent reservations can't both read the spend from before the other's row. A reservation that times out fails closed with `SpendCapReachedError`.

### Clustering

`apps/api/src/modules/clustering/` groups stories that report the same event. `ClusteringStep` is the first post-run step (before the rank recompute) and runs when both `FEATURE_CLUSTERS` and `AUTO_CLUSTERING` are on. It decides the stories this run created (`firstSeenAt` at or after the run's start on the database clock), one at a time in `publishedAt`, then `id` order:

1. **Pre-filter.** `ClusterPoolService` loads once per run every story within ±72 h of the new ones, with its cluster's size, and computes each story's entity tokens, title trigrams and CVE/GHSA ids once. `rankClusterCandidates` (`packages/shared/src/core/clustering.ts`) scores `0.45·trgm + 0.45·ent + 0.10·link` in memory (`trgm` is `pg_trgm`'s similarity, computed in TypeScript; `link` is the same project URL or a shared advisory id), offers each cluster once through its best member, skips clusters of 12, drops scores under `CLUSTER_CANDIDATE_MIN_SCORE` and keeps the top 5. This run's not-yet-decided stories are left out. No candidate means no model call and a `null` `clusterScore`.
2. **Decision.** One `LlmService.generateStructured` call (feature `cluster`, `refId` the story, the run's signal) with the `clusterMatch.v1` prompt: S and the candidates in `<source>` blocks, the candidates labelled `c1`..`c5` and mapped back by the server. `clusterDecision` joins S to the matched candidate at confidence `CLUSTER_MIN_CONFIDENCE` or more; `clusterScore` stores the confidence, or 0 for `none`.
3. **Writes.** `ClusterMembershipService` writes each decision in one transaction: S joins the matched story's cluster (read again inside the transaction; a conditional update keeps it at 12 or fewer), or pairs with the matched single story in a new `Cluster` whose representative is that story. Two multi-member clusters never merge. Choosing the representative again and the cluster's rank upkeep belong to the cluster feed issue (#79), which merges before or together with this step.
4. **Fail-safe.** `clusterFailureAction`: a spent cap or a provider error stops the step for the run; invalid or refused output leaves that story single and moves on; an unexpected error is logged, leaves that story single, and stops the step after three in a row. A run makes at most `CLUSTER_MAX_CALLS_PER_RUN` calls. The run's signal is checked before each call and aborts the one in flight, and a story is never decided in a later run.

### Summaries

`apps/api/src/modules/summaries/` builds a story's TL;DR and community consensus. `SummariesService.generate(storyId, trigger, { userId?, signal? })` returns `{ kind: 'cached' | 'created', summary }`: a story with a `Summary` row is answered from it with no fetch and no LLM call, and only a successful call writes a row.

1. **Inputs.** `SummaryInputsService.collectSummaryInputs` loads the story and its own source items (with `FEATURE_CLUSTERS` on, those of every member of its cluster, the representative's first): each HN item's comment tree from HN Algolia (`GET /api/v1/items/{id}`, at most 4 in flight across all summaries), each Dev.to item's comments (`GET /api/comments?a_id=`), and one Dev.to article body (`GET /api/articles/{id}`) as the text: the representative's first Dev.to item's, else the first Dev.to member's in `rankScore` order, else the first excerpt in member order. Dev.to requests go through `common/devto/DevtoClient`, whose one serial queue ingestion's Dev.to adapter shares. A malformed comment is dropped and counted; any failed fetch cancels the story's other fetches and throws `SummaryInputsUnavailableError`, scoped to the `story` (a 404 or malformed payload) or its `upstream` (5xx, 429, timeout, an aborted signal).
2. **Prompt.** `flattenComments` orders the comments breadth-first across the threads and trims them to their token budget; `llm/prompts/storySummary.v2.ts` puts the title, the text and each comment in its own `<source>` block and holds the system prompt (which tells the model to paraphrase and never quote), the output schema `StorySummaryLlmSchema` and the per-call budgets. A changed prompt is a new file with the next `PROMPT_VERSION`, which every `Summary` row stores. **No quotation.** `summaryRequest` wraps the schema per call in `noQuotationSchema`: a TL;DR point, pro or con that shares 8 or more consecutive words (`sharedRunFinder`, compared without case and punctuation, version strings and dotted names as one word) with the story's text as the prompt carries it or with one comment fails validation; words restating the title don't count. That is the schema retry of `LlmService`, so a copying reply costs its own ledger row and gets one more try before 502 `GENERATION_FAILED`; the JSON schema sent to the provider is unchanged.
3. **Call and store.** `LlmService.generateStructured` with feature `summary_auto` or `summary_on_demand`; the server adds `basedOnComments` and drops the consensus below 5 comments. A unique-key conflict with a concurrent call returns that call's row as `raced`.

**Clusters.** With `FEATURE_CLUSTERS` on, a cluster has one summary, stored on its representative. `findSummary` (`common/story-card/clusterSummary.ts`) is the one lookup: the newest `Summary` among a story's cluster members, or the story's own when it is single. `generate`, `GET /stories/:id/summary`, story detail, `ClusterDetail.summary` and `hasSummary` all use it, so a cluster with a summary on any member is `cached` for every member. A clustered `generate` is single-flight per cluster within the process (`SummariesService` keeps one in-flight promise per cluster id): concurrent requests for any member await it and answer `cached`, so they make one model call. Across instances the unique `Summary.storyId` decides.

`AutoSummariesStep` runs after the rank recompute and before the feed cache is cleared in every ingestion run, when both `FEATURE_SUMMARIES` and `AUTO_SUMMARIES` are on. It summarises the unsummarised Top-window stories in `rankScore` order, so every new story gets a summary. A candidate passes `hasSummaryInput` (below), then has at least `AUTO_MIN_COMMENTS` comments or was first seen at least `AUTO_SUMMARY_MIN_AGE_HOURS` ago, the age measured from the run's start on the database clock (`summaryRules.ts`); a cached summary is final, so a fresh thread first gathers some discussion. Stories (with clusters on, clusters) whose auto call failed today are left out. The step ends when `AUTO_SUMMARIES_PER_DAY` auto summaries exist for the UTC day, `AUTO_ATTEMPTS_PER_RUN` stories were tried, the HN items of the tried stories reach `AUTO_HN_REQUESTS_PER_RUN` requests, the `summary_auto` or global cap is spent, or the run's 4-min budget is spent; the cap binds before the count, and what is left over stays a candidate while it is in the Top window. With clusters on, a candidate is a primary story, judged by the comments and items of all its cluster's members and by its own age, whose cluster has no summary on any member. Each run logs one line with its attempts, the summaries created and its duration. `autoFailureAction` in `summaryRules.ts` decides each failure: a spent cap, a provider error or an upstream failure stops the step for the run; invalid or refused output and a story-scoped input failure skip to the next story. **Summary input.** `hasSummaryInput` is the one predicate for whether a story has enough to summarise: it takes stored items only, so it runs before any fetch, and is true when the story has a Dev.to item (an article body) or at least `SUMMARY_MIN_COMMENTS` HN comments, summed over cluster members (`common/summary-input/hasSummaryInput.ts`). A story that passes it but has no article text, excerpt or `SUMMARY_MIN_COMMENTS` comments once fetched is skipped with `NOT_FOUND` before any model call. The auto step, `POST /stories/:id/summary` and `StoryDetail.canSummarize` all call it, so a GitHub-only or RSS-only story and an HN story with too few comments are never summarised. `GET /api/v1/stories/:id/summary` serves a stored summary, and with `FEATURE_SUMMARIES` on, story cards carry `hasSummary`, `summaryLine` and `canSummarize`, and the story detail its `summary`. **Card line.** `summaryLine` is `tldr[0]` of the story's own summary, or with clusters on of the newest summary among the cluster's members (the `findSummary` order); it is `null` without a summary, never an excerpt. `toStoryCards` fills it for a whole page with `loadClusterSummaryInfo` (`common/story-card/clusterSummary.ts`): one query for the clusters' summaries, with no per-card query; `canSummarize` (`hasSummaryInput` over the cluster) comes from the members' items that `loadCardClusters` already reads, so a page costs two Prisma calls. A single story reads both from its own row and items. The card renders the line as clamped plain text under the title, and the feed binds `u` while the active card's `canSummarize` or `hasSummary` is true.

`POST /api/v1/stories/:id/summary` (`OnDemandSummaryService`) is the on-demand path: a stored summary answers 200 for free; otherwise a daily quota slot (20 per user, 5 per guest keyed by IP digest `sha256(ip + daily salt)` plus device id, in `RateLimitCounter`) is taken, `generate` runs, and the response is 201. A story with no summary and no `hasSummaryInput` is 404 `NOT_FOUND` before the slot is taken, with no model call. Over the quota is 429 `QUOTA_EXCEEDED`; the route also has a 5/min/IP window. The story page shows the result in `SummaryPanel`, which names the story's sources and links "Read the original on <domain> ↗" beside the AI label, with a Summarize button when none is stored and `canSummarize` is true, and with nothing when it is false. Choices: [DECISIONS](../DECISIONS.md).

### Copilot

`apps/api/src/modules/copilot/` answers a question with a streamed briefing. `BriefingPipelineService` (question → retrieval → streamed `BriefingPlan` → compiled A2UI messages) is wrapped by `CopilotService`, which `CopilotController` serves as `POST /api/v1/copilot/ask` (SSE, written on the raw Express response) and `GET /api/v1/copilot/quota`.

`ask` checks in this order:

1. **Before the stream (JSON errors).** The `FEATURE_COPILOT` flag, the Origin check, the 5/min/IP window and the body schema; then the **24 h cache**: the newest `complete` `CopilotQuery` with the same `questionHash` (sha256 of `normalizeQuestion`) is replayed as `meta { cached: true }`, its stored messages and `done`, with no quota, no row and no model call. Otherwise a **quota slot** is taken (`copilotQuota`: a user 20 per UTC day; a guest 3 per device and 10 per IP digest, both taken or neither), and a full counter is a 429 `QUOTA_EXCEEDED` with `resetsAt` and `Retry-After`.
2. **The stream.** The `CopilotQuery` row is created as `streaming` before the headers (a failure there is still a JSON 500 and gives the slot back); the headers and a `: ping` go out at once and a `: ping` follows every 15 s. The pipeline's first event decides the opening `meta`: its spend reservation has happened by then, so `meta` says whether this is a fallback.
   - `no_coverage`: the deterministic briefing, status `no_coverage`, slot given back.
   - `SpendCapReachedError` (the `copilot` cap or the global one): the closest `ExampleBriefing` (`closestExample`: most shared `tagStory` tags, ties by `position`) with `meta.fallback = 'SPEND_CAP'`, status `fallback`, slot given back; with no examples, `error { SPEND_CAP_REACHED }`.
   - Otherwise every compiled message is one `a2ui` event; at the end the row becomes `complete` with its messages, `storyIds`, tokens and cost, and `done { usage }` closes the stream.
   - A failure after the stream started (provider error, invalid plan, the 10 s first-token or 30 s total deadline of `LlmService`) sends `error { GENERATION_FAILED }`, stores `failed` (never replayed) and gives the slot back only when no section component was written; the opening `root` alone is not one. An unexpected error sends `meta` if none went out yet, then `error { INTERNAL }`. A client hang-up sends no error event: the row is stored as `failed` under the same slot rule.
3. **Disconnects.** The response's `close` aborts the pipeline's `AbortSignal`, which aborts the model call; the service still stores the row and settles the slot. The model call's `LlmUsage.refId` is the `CopilotQuery` id, and the row's `guestKey` is `sha256(ip digest + deviceId)`.

Every event payload is parsed with its shared schema before it is written. Choices: [DECISIONS](../DECISIONS.md).

## Clusters

A cluster is a `Cluster` row plus `clusterId`, `isPrimary` and `clusterScore` on its member stories (written by the clustering step). The read side keeps three things current:

- **Rank.** `planRankUpdates` counts `k` for a clustered story over `Cluster.sourceKinds`, so every member carries the same cross-source bonus. After scoring, each cluster with a member in the Top window takes its best-scored member (ties by `id desc`) as representative; only members inside the window compete. `RankingService` then writes `Cluster.representativeStoryId`, `Cluster.rankScore` (the representative's `rankScore`) and `Cluster.sourceKinds` (the union of the members' current kinds) and leaves `isPrimary` true on that member only, all in one transaction batch per cluster. With `FEATURE_CLUSTERS` off the recompute ignores clusters.
- **Retention.** The daily cluster upkeep step runs after the 90-day purge and finds broken clusters in the database (`clusterNeedsUpkeep`: fewer than two members, a wrong count, or not exactly the representative primary). `planClusterUpkeep` (`dailyRules.ts`) decides each: recount `memberCount` and `sourceKinds` and re-pick the representative, or, with fewer than two members left, delete the cluster and reset the remaining story to a single primary story (its `clusterScore` stays).
- **Reads.** With `FEATURE_CLUSTERS` on, every feed query shape filters `isPrimary = true` (the `(isPrimary, rankScore, id)` index), so a cluster is its representative's one card and filters, mutes and follows act on the representative. Cards carry `cluster`, loaded for a page in one query (`common/story-card/clusterCards.ts`); `GET /stories/:id` adds `clusterMembers`, and `GET /clusters/:id` returns the representative and the other members. With the flag off none of these fields is sent.
